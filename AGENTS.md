# Ontology as Specification: rules for agents

This repository describes an approach to product development: product meaning kept as a semi-formal ontology with permanent concept IDs, referenced by every artifact and checked by a script. Read `README.md` first.

<!-- ont: ent.doc-set@ca5d70, ent.reference-page@b1ec8f, ent.tool-copy@cea475 -->
## Layout

- `docs/` explains the approach: principles, the ten parts, lifecycle, comparison, limitations. It is a doc set of the approach's ontology: sections carry anchors, and `docs/reference.md` is generated. A rule of the approach is changed in `ontology.md` and `checks.md`, then explained here; never edit `docs/reference.md`.
- `example/` is a fictional lending library described with the approach, end to end.
- `templates/` holds starting files; the set must pass the check.
- `tools/ont-check/` is the check, the decision guard, and the generators of tooltips, contracts, reference pages and the approach's IDs (`approach.json`, copied with the tool), with tests.
- `ontology.md` and `checks.md` describe the approach with itself: its concepts, rules and checks. `ont.config.json` checks them; the tests in `tools/ont-check/test/` implement the checks.
- `decisions.md` records decisions about this repository.

## Rules

- **English only** (D-03).
- **Nothing from the source project.** Do not copy content, names, concepts, decisions or screens from the product where the approach emerged, and do not name it (D-01, D-02, D-45). Examples use the fictional lending library or generic placeholders. No personal data, no names of partners or contractors.
- **The ontology first.** A change to the approach starts in `ontology.md` and `checks.md`; the docs, the tools and their tests are written from them after. What a page or a tool would say or do that the ontology does not is added to it first, or asked (`rule.ontology-changes-first`, `rule.ontology-is-source`, D-73).
- **Review before merge.** Before a change is merged, an agent of another provider that did not write it gives a verdict to the checks of review and of run `node tools/ont-check/ont-check.mjs --config ont.config.json --review main` lists, with `skills/change-review/SKILL.md`: a check of review by reading the change, a check of run by carrying it out with its section of `docs/run-guide.md` (`rule.reviewed-before-merge`, D-165). What follows the one narrow round after the confirmed condition, a merge at once after a clean one, fixes, one issue of verdicts and a record of done after one with findings, is said in one place, `docs/parts/agent-rules.md`, "After the narrow round" (`rule.ready-after-clean-round`, `rule.fixes-held-by-tests`, D-164, D-165).
- **New mechanisms need a decision.** A new check, generator or format rule is recorded in `decisions.md` before it is implemented (D-56).
- **Unapproved is tentative.** A choice the owner has not explicitly approved is recorded as tentative; the owner's approval accepts it (`rule.unconfirmed-tentative`, D-34). A question with a recommendation is written as a tentative entry, and the owner's answer accepts it (`rule.question-as-tentative`, D-48).
- **Sources.** From D-47 on, every accepted entry names its source on a `- Source:` line: the owner's answer or message that decided it (`inv.sourced-since-first`, `rule.source-precedence`, D-47). What is put off gets a `- Return when:` line (`rule.deferral-returns`, D-49).
- **Accepted decisions are never edited**, here or in the example. Write a superseding entry; `npm run guard` refuses the edit (`inv.accepted-never-edited`). One entry answers one question; a later entry adds to it or supersedes it whole (`rule.one-choice`, D-26).
- **A task under its statement and budget.** Before each step and each round of a task, run `node tools/ont-check/ont-check.mjs --config ont.config.json --task <task> --statement <file>`; the records of the process, rounds, verdicts, done, the owner's approval and the gate records, are written by the tool's writers with their seals, never by hand (`rule.records-by-tool`, D-167): work starts only under an approval in force, an exhausted budget is a question to the owner, and a result is accepted only after `done.mjs` recorded done (`rule.work-under-approval`, `rule.budget-before-next`, `rule.acceptance-against-approved`, D-164, D-108).
- **Commit every change.** Every change ends with a commit of its own files, never another agent's (`rule.commit-finished-work`, D-54).
- **Strongest step.** A correction is held by the check, a test or the structure of the code where one of them can hold it; a rule here only where none can (`rule.strongest-step`, D-67).
- **Findings that matter.** A consistency review reports what would mislead a reader or an agent, or would break a check. Style, the completeness of lists and compliance that changes nothing are not findings (`rule.findings-mislead`, D-27).
- **Cite primary sources.** A claim about another tool or practice links to its primary source; quotes are verbatim.
- **Keep the example consistent.** It follows its own rules in `example/AGENTS.md`. After editing the example's definition rows, run `npm run format` and `npm run generate` to regenerate the tooltips, the contracts and the reference pages (D-04).
- **Merge through the gate.** Main changes only through a pull request that passed `ont-check` and `ont-gate-guard` on its head, on a branch up to date with main (`rule.main-through-gate`, D-165). A change of a gate path, `mergeGate.paths` of `ont.config.json`, is allowed only by an item of What to do of the approved version of a task's statement: commit it, then a record of a gate change in `reviews/tasks/`, written by `node tools/ont-check/gate-record.mjs change` for each item, naming the task, the version's hash, the item, the paths and that commit, the last of the pull request outside `reviews/`, never a later record of done, and after it only records (`inv.gate-change-approved`). Before the merge, run `node tools/ont-check/merge-gate.mjs records-only --reviewed <commit the reviewer of the result checked> --head <head> --base <main>`, again after updating the branch with main, with the commit `docs/parts/agent-rules.md`, "After the narrow round", names as the one to compare with when the step ended after a narrow round (`rule.fixes-held-by-tests`); then merge through the API by a merge commit with the head's commit as its condition, `gh api -X PUT repos/<owner>/<repo>/pulls/<n>/merge -f merge_method=merge -f sha=<head>` (`rule.merge-what-was-checked`).
- **Switch the gate on.** After the merge of the task that brings the gate, run `node tools/ont-check/merge-gate.mjs switch-on --repo <owner>/<repo>` and take the steps it prints from `.github/merge-gate.json`, in their order, each with its `gh api` calls, stopping where a readback differs from the rule file. The positive proof is the merge of the next task's pull request (`rule.gate-switched-on`, D-163).
- **The tree after a merge on GitHub.** A merge on the server runs no hook in any clone. After each one, in the clone that serves the ontology tree, on main, or in a temporary worktree of main when that clone is on another branch: confirm that `git config --path ont.treeOut` gives an absolute path; run `git pull --ff-only`; confirm that `git rev-parse HEAD` is the merge commit and equals `git rev-parse origin/main`; run `node tools/ont-check/gen-tree.mjs --stale`, and when it reports the tree stale, `node tools/ont-check/gen-tree.mjs --refresh` and `--stale` again; then confirm that the page's footer, `built from`, names the merge commit, since `--stale` says nothing of a fresh tree (`rule.tree-after-server-merge`, D-165).
- **Rules name their source.** A process rule here that comes from a rule of the approach or from a decision names it, by ID or entry; a departure from the approach is a process entry with `Extends:` or `Overrides:`. `npm run check` fails on an ID or entry named in this file that does not exist, is retired or is superseded (`rule.agent-rule-source`, `rule.departure-by-entry`, D-53).

## Verify

```bash
node tools/ont-check/ont-check.mjs --config ont.config.json             # ONT_OK: the approach itself
node tools/ont-check/ont-check.mjs --config example/ont.config.json --run   # ONT_OK, and every trace passes on the oracle
node tools/ont-check/ont-check.mjs --config templates/ont.config.json   # ONT_OK
node --test 'tools/ont-check/test/*.test.mjs' 'example/app/*.test.mjs' 'example/e2e/*.test.mjs'
```

`npm test` runs all four and the guard. A change to a rule of the approach starts in `ontology.md` and `checks.md`, like any product change. `npm run guard` compares accepted decision entries with `HEAD`. `npm install` enables the hooks of the clone, setting `core.hooksPath` to `.githooks` (`rule.early-pre-commit`, D-165); pre-commit runs the check on the content of the commit, its index, whatever paths it changes, and the guard, as an early signal that `--no-verify` skips, while only the checks on the server hold a merge; and post-merge rewrites the ontology tree from the files of `HEAD` after a merge into main where the clone sets `ont.treeOut`, and writes nothing, naming the files, when the working tree's copies differ from them at the paths the configuration gives, or the generator's files are missing (D-105, D-137). Git runs `post-merge` only when `git merge` or `git pull` itself makes the merge commit or the fast-forward, so not after `git merge --continue`, a `git merge --no-commit` committed apart, or a real rebase; after those, run `node tools/ont-check/gen-tree.mjs --refresh` on main, and `--stale` says whether the tree shows main.
