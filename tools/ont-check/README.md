# ont-check

The drift check, the decision guard, and the generators of tooltips, contracts, reference pages and the ontology tree. Node 20 or later, no dependencies. Copy the directory into a project with `pin.mjs update`, `approach.json` included: it holds the approach's own IDs, which agent instructions and process entries name. What it checks and why is described in [part 5](../../docs/parts/drift-check.md).

```bash
node tools/ont-check/gen-glossary.mjs --config path/to/ont.config.json   # glossary → generated tooltips
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json   # ONT_OK, or the drift and exit code 1
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --coverage   # also: what proves each implemented concept
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --gap [ticket.md]   # also: the work left and what each target waits for, or one ticket's slice (exit 1 until done)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --next   # also: the next slice of what is ready, as IDs: and Checks: lines for a ticket
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --decisions   # also: every decision entry, in force, tentative or superseded, and the later entries that name it
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --review main   # also: the manual checks a change since main touches, the project's and the approach's, for a reviewer (D-77)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --review main --record verdicts.md   # also: writes the records of the reviewer's table of verdicts into manualRuns (D-100)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --rounds   # also: what follows the last round of each task's review, and the payoff of each step after ten applications (D-99)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --task TASK [--statement FILE]   # also: what the task needs next, its statement, its result and its budget; run it before every step and every round (D-106, D-108)
node tools/ont-check/done.mjs TASK --statement FILE [--config path/to/ont.config.json] [--commit REF]   # runs the statement's Done-when: commands on the commit (default HEAD) in a temporary worktree and writes the record of done into taskRecords, only under an approval in force and when all pass (D-107)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --mutate   # also: changes one line of a form at a time; lists the changes no trace fails on, and fails on a test of systemTests that passes on a change its check's trace fails on (D-102)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --run   # also: runs every trace of the catalogue on the oracle, the ontology's formal forms (D-93); needs "oracle": true
node tools/ont-check/format-ontology.mjs --config path/to/ont.config.json   # kind order, Kind cells and aligned definition tables
node tools/ont-check/gen-contracts.mjs --config path/to/ont.config.json   # field and relation types → JSON Schema
node tools/ont-check/gen-reference.mjs --config path/to/ont.config.json   # reference pages from the ontology and the checks
node tools/ont-check/gen-tree.mjs --config path/to/ont.config.json --out tree.html [--labels labels.json]   # the whole ontology as a tree for people, not kept in the repository; the footer marks the commit, +working-tree or no-commit (D-105)
node tools/ont-check/gen-tree.mjs --refresh [--squash]   # what the post-merge hook runs: on main, the tree at the clone's `ont.treeOut` from the root ont.config.json; --squash, given by the hook after a squash merge, writes nothing and says why
node tools/ont-check/gen-tree.mjs --stale   # why the tree at `ont.treeOut` does not show refs/heads/main, or nothing; always ends with 0
node tools/ont-check/gen-approach.mjs  --config ont.config.json   # in the approach's own repository: approach.json from its ontology
node tools/ont-check/stamp-docs.mjs  --config path/to/ont.config.json [page.md …]   # after rereading: stamp the anchors
node tools/ont-check/guard-decisions.mjs --config path/to/ont.config.json [--base REF] [--staged]   # GUARD_OK, or GUARD_OFF before the first commit; lists accepted entries not committed yet
node path/to/ontology-as-spec/tools/ont-check/pin.mjs update --dir tools/ontology-as-spec [--pin FILE] [--ref REF] [--from CLONE] [--dry-run]   # copy the tool from commit REF (default HEAD) of its clone, or of --from, and write the pin; --dry-run only prints what changes
node tools/ontology-as-spec/pin.mjs verify [--dir DIR] [--pin FILE]   # fails on a file of the copy that is missing, changed or not in the pin; the pin is upstream.json in the copy's directory unless --pin names another
```

Without `--config`, every script looks for `ont.config.json` in the current directory. A ticket path after `--gap` is relative to the current directory. The guard also takes `--file path/to/decisions.md` for a log without a config, and several `--config` and `--file` arguments at once.

## Formats it expects

- **Definition rows:** ``| Kind | `class.name` | Term | Definition |``, anywhere in the ontology. A table is a run of consecutive table lines; the Kind cell holds no backticks. Together the rows are the glossary.
- **Type cells:** a fifth column, ``| Kind | `id` | Term | Type | Definition |``. Vocabulary: `text`, `number`, `boolean`, `integer` with optional bounds (`integer 0..2`, `integer 1..`), `date`, `datetime`, `one of a, b, c`, ``ref `ent.x` ``, ``refs `ent.x` ``, each optionally followed by `optional`.
- **Retired IDs:** ``| `old.id` | `new.id` | D-nn |`` under `headings.retired`; a dash instead of the new ID for a removed concept.
- **IDs in Markdown text:** in backticks; other text is not read as IDs. Doc anchors and test tags, below, have their own forms.
- **Implementation rows:** ``| `class.name` | `path`, `path` | note |`` inside the implementation section. Concepts realised in the same files may share a row: ``| `class.a`, `class.b` | `path` | |``.
- **Known divergences:** bullets under a heading that starts with `headings.divergences`, by default `### Known divergences`, each naming the concepts involved in backticks; the check fails on a line that names none. `--gap` prints them. With a ticket it prints only those naming its concepts: a line that names only concepts of the slice keeps it open, and one that also names other concepts is shown apart and not counted.
- **Mockup:** `data-ont="class.name"` attributes, and IDs in single quotes inside scripts (`'view.catalog'`). IDs built from templates are declared in a comment `/* data-ont dynamic: 'class.a','class.b' */`, and the markup must contain `data-ont="class.${`.
- **Decision entries:** headings matched by `decisions.entry`.
- **Checks:** ``| `check.section.name` | `id`, `id` | GIVEN | WHEN | THEN | auto, judged or manual | covers |``, the last cell optional: the axis values the check covers, `refusal` or `time: days later`. A line `- Cannot occur: `action.id` value — why` rules a value out for the concepts it names, or for every concept when it names none; a line without a value or without a reason after the dash fails. under `## Section` headings; the second part of the ID is the section's key: the code span in the heading (``## Préstamo `loan` ``), one span of lowercase letters, digits and hyphens, or else the heading's Latin letters and digits in lowercase, joined by hyphens. Each ontology section with definition rows needs a key of its own, and every catalogue section's key must name one of them.
- **Scenario files (older):** an `IDs:` line at the start of a line.
- **Test tags:** IDs in square brackets anywhere in a test file, normally at the start of a test title: `test("[check.loan.renew-while-held] …")`, or a concept for what is not a product check, `test("[field.loan.renewals] …")`. Only `check` and configured classes are read, so `[0]` or `[x.y]` is not a tag.
- **Tickets:** an `IDs:` or `Ontology IDs:` line, and a `Checks:` line with the checks of the slice in backticks. A check named elsewhere in a ticket must exist but is not part of the slice. Older tickets may have a `## Scenarios` section whose bullets read `- [id, id] GIVEN … WHEN … THEN …`.
- **Doc anchors:** `<!-- ont: id, id@stamp -->` in pages of a doc set, outside code blocks and inline code; IDs are concepts or checks, stamps are optional and written by `stamp-docs.mjs`.
- **Supersession:** an entry that replaces older ones names them on a line matched by `decisions.supersedes`, by default `- Supersedes: D-05, D-07`. The line of a tentative entry takes effect when the entry is accepted.
- **Decision status (guard):** an entry is accepted when one of its lines matches `decisions.accepted`, by default a `- Date:` line containing `Status: accepted`. The check lists the entries that are not, as waiting for the owner's answer.
- **Sources (guard):** a line matched by `decisions.source`, by default `- Source: call of 2026-10-24, 00:41`. Once any entry has one, the guard fails on an entry accepted since its base without one, new or accepted from tentative; when the first source is newer than the base, only entries numbered after it are asked.
- **Code names:** `ont: id, id` in a comment of the code that implements the concepts, `// ont: rule.renewal`, in the files of the implementation table and of the directories under `code`. A stamp after `@` is ignored, so a doc anchor in such a file names its concepts too, and may name checks of the catalogue. Only the IDs after the marker are read, so a property path in code that looks like an ID is not one, and each must resolve, whatever its class. The marker is read as text, in any comment syntax and inside a string too; in Markdown, code blocks and inline code are examples and are not read.
- **Agent instructions:** IDs in backticks, of the project's ontology or of the approach, and entries of the project's log by the pattern of `decisions.ref`. In them `D-nn` is always an entry of the project's log; a rule of the approach is named by its ID. The project's retired IDs come first, and file names such as `action.yml` are not IDs.
- **Process entries:** `- Layer: process`, and `- Extends:` or `- Overrides:` with the IDs of the rules of the approach in backticks. Every such line is checked, and an empty one fails; a superseded entry may name a rule the approach has retired since.
- **Deferrals:** a line matched by `decisions.returnWhen`, by default `- Return when: a second branch opens`. The check lists every accepted deferral in force with its condition, as information.

## Hooks

Run the check on commits that touch any file it reads, the code paths that implement concepts among them: it reads their `ont:` names, and a change there is a reminder to update the implementation table. Run the guard with `--staged` on every commit, and in CI with `--base` set to the commit before the push or the base of the pull request. This repository's own hooks are `.githooks/pre-commit` and `.githooks/post-merge`, which rewrites the ontology tree after a merge into main where a clone sets `ont.treeOut`, and its CI is `.github/workflows/check.yml`; enable the hooks with `git config core.hooksPath .githooks`.
