# ont-check

The drift check, the decision guard, and the generators of tooltips, contracts, reference pages and the ontology tree. Node 20 or later, no dependencies. Copy the directory into a project with `pin.mjs update`, `approach.json` included: it holds the approach's own IDs, which agent instructions and process entries name, and its checks of review and of run, which `--review` hands to a reviewer. Update the copy with the `pin.mjs` of the version you update to, then move your files to its format (`rule.tool-before-files`). What it checks and why is described in [part 5](../../docs/parts/drift-check.md).

```bash
node tools/ont-check/gen-glossary.mjs --config path/to/ont.config.json   # glossary → generated tooltips
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json   # ONT_OK, or the drift and exit code 1; every ERROR it prints, of a flag or of the configuration a flag needs too, fails the run with no ONT_OK (D-129)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --coverage   # also: what proves each implemented concept
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --gap [ticket.md]   # also: the work left and what each target waits for, or one ticket's slice (exit 1 until done)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --next   # also: the next slice of what is ready, as IDs: and Checks: lines for a ticket
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --decisions   # also: every decision entry, in force, tentative or superseded, and the later entries that name it
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --review main   # also: the checks of review and, apart, of run a change since main touches, the project's and the approach's, each check of run with its guide, for a reviewer (D-165)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --review main --record verdicts.md   # also: writes the records of the reviewer's table of verdicts into the directory of verdicts, each pass or fail with its Performer (D-100, D-165)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --rounds   # also: for every task any record names, the counts of its rounds and the lines of --task given no file, and the payoff of each step after ten applications (D-99, D-152)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --task TASK [--statement FILE]   # also: what the task needs next, its statement, its result and its budget; run it before every step and every round (D-106, D-108)
node tools/ont-check/done.mjs TASK --statement FILE [--config path/to/ont.config.json] [--commit REF] [--evidence FILE]   # runs the statement's Done-when: commands on the commit (default HEAD) in a temporary worktree and writes the record of done into taskRecords, only under an approval in force and when all pass; --evidence writes the file's lines, what the statement asks done to name such as each changed row of the catalogue, under Evidence: (English and repository paths only where records.latinOnly is set, D-166) (D-107)
node tools/ont-check/round.mjs brief TASK --step statement|result --statement FILE [--config path/to/ont.config.json]   # the brief of the next round, only when it is the task's next action; its lines go first in the reviewer's brief (D-168)
node tools/ont-check/round.mjs record TASK --from REPLY --triage FILE [--step statement|result] [--statement FILE] [--config path/to/ont.config.json]   # the record of the round from the reviewer's reply, which begins with the brief's lines, and the executor's triage of every finding, with its snapshot of spend (D-168, D-169)
node tools/ont-check/round.mjs fixes TASK --round FILE --from FILE [--config path/to/ont.config.json]   # the record of the tests that hold the fixes of a round's findings, by class (D-168)
node tools/ont-check/spend.mjs TASK --statement FILE [--config path/to/ont.config.json]   # the spend of the task and of its goal from the session logs, with the marks it passed (D-169)
node tools/ont-check/approve.mjs TASK --statement FILE --question N --kind approval|gate [--round FILE] --english FILE [--config path/to/ont.config.json]   # the owner's approval or answer to a gate from the registry, by the command in ONT_REGISTRY_CMD (D-170)
node tools/ont-check/gate-record.mjs change TASK --statement FILE --clause N --paths PATH,PATH --base REF [--refresh] [--config path/to/ont.config.json]   # records of a gate change of the final diff of the branch, one for each item; --refresh writes them again on a new HEAD (D-170)
node tools/ont-check/gate-record.mjs proof TASK --gate GATE --check CHECK --pr N --kind refusal|pass --repo OWNER/REPO [--response FILE] [--base SHA] [--config path/to/ont.config.json]   # a gate proof from the pull request and its runs, by gh api or ONT_GH_CMD; the base of a pass is its merge's first parent, of a refusal --base (D-170, D-180)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --run-start CHECK   # before a run of a check of run outside a review: keeps HEAD, and refuses a working copy that differs from it outside the records (D-171)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --run-record CHECK --verdict pass|fail --performer agent --by WHO --evidence WHERE   # after it: the verdict record, Origin: run, with its seal, refused when anything outside the records changed since --run-start (D-171)
node tools/ont-check/merge-gate.mjs guard --base SHA --head SHA [--config path/to/ont.config.json]   # the guard of the merge gate: refuses a pull request whose diff changes a gate path (mergeGate.paths) without a record of a gate change for the approved version; reads the pull request only as data (D-165)
node tools/ont-check/merge-gate.mjs records-only --reviewed SHA --head SHA [--base SHA] [--config path/to/ont.config.json]   # before a merge: outside reviews/, the head's tree is the reviewed commit merged with --base as Git merges them; a resolution that changes it, a conflict outside reviews/ or a head without the base is refused, and a failed Git command is an error; after the narrow round that follows a confirmed condition, the commit of the record of done that ends the range of fixes stands for --reviewed (rule.fixes-held-by-tests, D-165)
node tools/ont-check/merge-gate.mjs ruleset [--config path/to/ont.config.json]   # prints the ruleset of main from the rule file (mergeGate.rules), for gh api --input - (D-165)
node tools/ont-check/merge-gate.mjs switch-on [--repo OWNER/REPO] [--config path/to/ont.config.json]   # prints the steps that switch the gate on after the merge of the task that brings it, in their order, each with its gh api calls, from the rule file: the event policy for pull_request_target first (D-163)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --releases   # also: each release of the product and, for each environment, the release running now (D-111)
node tools/ont-check/release.mjs 0.2.0   # in the approach's repository, in a clean work tree: npm test and the check on HEAD, then the release commit that adds the entry of releases.md, tagged v0.2.0 (D-109)
node tools/ont-check/release.mjs --resume   # tags a release commit left without its tag, after its shape is checked and npm test and the check pass again on its parent in a temporary worktree
node tools/ont-check/release.mjs --product 1.0.0 [--config path/to/ont.config.json] [--commit REF]   # runs the check and the test suites of the configuration of the commit in a temporary worktree and writes the record of the release into releases.dir only when none failed or ran no test, a suite whose tests were skipped recorded as skipped with how many; a commit outside the history of HEAD refused before anything runs, and the record validated by the check's own function before it is written (D-111, D-116, D-125)
node tools/ont-check/release.mjs --verify 1.0.0 [--config path/to/ont.config.json]   # checks the integrity of the whole version first, every record of it, read or not (D-127), then runs the checks of a release again on its commit and compares them with its record, a skipped suite with the same counts: the only proof that they ran (D-116, D-125)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --mutate   # also: changes one line of a form at a time; lists the changes no trace fails on, and fails on a test of systemTests that passes on a change its check's trace fails on (D-102)
node tools/ont-check/ont-check.mjs    --config path/to/ont.config.json --run   # also: runs every trace of the catalogue on the oracle, the ontology's formal forms (D-93); needs "oracle": true
node tools/ont-check/format-ontology.mjs --config path/to/ont.config.json   # kind order, Kind cells and aligned definition tables
node tools/ont-check/gen-contracts.mjs --config path/to/ont.config.json   # field and relation types → JSON Schema
node tools/ont-check/gen-reference.mjs --config path/to/ont.config.json   # reference pages from the ontology and the checks
node tools/ont-check/gen-tree.mjs --config path/to/ont.config.json --out tree.html [--labels labels.json]   # the whole ontology as a tree for people, not kept in the repository; the footer marks the commit, +working-tree or no-commit (D-105)
node tools/ont-check/gen-tree.mjs --refresh [--squash]   # what the post-merge hook runs: on main, the tree at the clone's `ont.treeOut` from the root ont.config.json and the ontologies as HEAD holds them, and only when the working tree holds the same files at the paths the configuration gives, never normalised, else it names those that differ, a path with `..` or a link among them, and writes nothing; --squash, given by the hook after a squash merge, writes nothing and says why
node tools/ont-check/gen-tree.mjs --stale   # why the tree at `ont.treeOut` does not show refs/heads/main, or nothing; always ends with 0
node tools/ont-check/gen-approach.mjs  --config ont.config.json   # in the approach's own repository: approach.json from its ontology
node tools/ont-check/stamp-docs.mjs  --config path/to/ont.config.json [page.md …]   # after rereading: stamp the anchors
node tools/ont-check/guard-decisions.mjs --config path/to/ont.config.json [--base REF] [--staged]   # GUARD_OK, or GUARD_OFF before the first commit; lists accepted entries not committed yet
node path/to/ontology-as-spec/tools/ont-check/pin.mjs update --dir tools/ontology-as-spec [--pin FILE] [--ref REF] [--from CLONE] [--dry-run]   # copy the tool from commit REF (default HEAD) of its clone, or of --from, and write the pin and copy.json, the commit the copy came from; --dry-run only prints what changes
node tools/ontology-as-spec/pin.mjs verify [--dir DIR] [--pin FILE]   # fails on a file of the copy that is missing, changed or not in the pin; the pin is upstream.json in the copy's directory unless --pin names another
```

A clone of a project that names its local clone of the approach with `git config --local ont.approachClone <path>` learns from the check, as information, which releases that clone knows are newer than the pin, read by their tags, with their changes and those that change the project's rules; it uses no network, so run `git fetch --tags` in that clone to learn of new ones (D-110).

Without `--config`, every script looks for `ont.config.json` in the current directory. A ticket path after `--gap` is relative to the current directory. The guard also takes `--file path/to/decisions.md` for a log without a config, and several `--config` and `--file` arguments at once.

## Configuration

Paths are relative to the config file.

| Key                                                            | Meaning                                                                                                                                                                                                                                                                                                                                                                      | Required |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `classes`                                                      | allowed ID classes in the order rows are grouped, either a list (`["ent", "field", "view"]`) or an object of class and Kind label (`{"ent": "Entity", "field": "Field"}`); with labels the Kind cells are checked                                                                                                                                                            | yes      |
| `scoped`                                                       | classes whose IDs name their entity (`["field", "edge"]`): `field.loan.due-date` must sit in the table of `ent.loan`                                                                                                                                                                                                                                                         | no       |
| `ontology`                                                     | the ontology Markdown file                                                                                                                                                                                                                                                                                                                                                   | yes      |
| `headings.retired`                                             | heading of the retired IDs table; default `## Retired IDs`; the section may be absent                                                                                                                                                                                                                                                                                        | no       |
| `headings.implementation`                                      | heading of the implementation table; default `## Implementation status`; `null` until code exists                                                                                                                                                                                                                                                                            | no       |
| `headings.history`                                             | heading of the ontology's revision history, whose new lines the guard reads; default `## Revision history`                                                                                                                                                                                                                                                                   | no       |
| `headings.otherWords` | heading of the table of other words people use for a concept (D-91); default `## Other words`; the section may be absent |
| `headings.divergences`                                         | the start of the heading of the known divergences; default `### Known divergences`; the section may be absent                                                                                                                                                                                                                                                                | no       |
| `root`                                                         | base directory for paths in the implementation table; default the config's directory                                                                                                                                                                                                                                                                                         | no       |
| `code`                                                         | code directories whose `ont:` names the check also reads, besides the files of the implementation table: `[{"dir": "src", "match": "\\.ts$"}]`                                                                                                                                                                                                                               | no       |
| `reviewPaths`                                                  | directories of data, such as cases with their sources, and the concepts a change of their files touches for `--review`: `[{"dir": "cases", "concepts": ["edge.case.sources"]}]`; each concept must have a check of review or run, or one still `manual` (D-80, D-165)                                                                                                                                                | no       |
| `verdicts.dir`                                                 | directory of the verdict records, one file per verdict on a check of review or run; the check lists the checks of review and run of implemented concepts without a current record (D-165) |
| `verdicts.require`                                             | when `true`, a check of review or run of implemented concepts without a current record fails the check |
| `manualRuns.dir`                                               | the earlier name of `verdicts.dir`, read as it; the check says to rename it, and a configuration with both keys is an error (`rule.tool-before-files`, D-165) |
| `manualRuns.require`                                           | the earlier name of `verdicts.require`, read as it |
| `records.latinOnly`                                            | when `true`, a verdict record or a record of a round holding a letter of a script other than Latin is refused, by the check and by `--record`; a project's rule of language, not the approach's (D-151). A path outside the repository is refused in every project                                                                                                            | no       |
| `records.sealsFrom` | when `true` at the base of a pull request, the guard requires a valid seal of every record of the process the pull request adds whose time is after the commit of the base's first-parent history that brought the key in, and refuses it with `SEAL_MISSING` or `SEAL_WRONG`; the full check and pre-commit say it as information (D-167) |
| `spend.fromLogs` | when `true`, spend is counted again from the session logs each time, the directories in `ONT_CLAUDE_LOGS` and `ONT_CODEX_LOGS`, the executor's sessions in `ONT_EXECUTOR_SESSIONS` and a goal's statement in `ONT_GOAL_STATEMENT`, all from the environment; `--task`, `--rounds`, `round.mjs` and `done.mjs` ask it first, only `--task` names an action by it, and the writers refuse without an input they need (D-169) |
| `goals` | the goals and their tasks, `{ "<goal>": ["<task>", …] }`, the composition of each goal: a task is counted with a goal only when its statement names it on `Goal:`, and a statement with no line is its own unit; a line `Goal:` of a statement, a kept brief or a record of done that names a goal not listed here, or one whose list does not hold the task, and a task listed under two goals are errors; a goal's own commands count all its tasks listed here (D-169, D-179) |
| `statements.todoHeadings` | the headings of the section What to do of a task's statement, whose numbered items `gate-record.mjs change --clause` names; default `["What to do"]` (D-170) |
| `mergeGate.codes` | for each task whose gate a gate proof probes, the codes of the guard its rules print, `{ "<task>": ["SEAL_MISSING", …] }`; a refusal counts only when the output of the check holds one of them and no code of another gate (D-170) |
| `reviewRounds.dir` | directory of the records of review rounds, one file per round; `--rounds` reads them (D-99) |
| `reviewRounds.gatesFrom` | a UTC time to the second, the time the project adopts the rules of D-152: a finding `not fixable` in a round before it carries its earlier meaning, not fixable within the task, and opens no gate over the task; a round of either step at or after it must give `Statement-hash:`, or it cannot be read and blocks every task, while an older round without it reads as it did. Without the key every round carries the meaning of D-152, so every round without `Statement-hash:`, an old one too, cannot be read: a project with such records sets the key to the time it adopted the rule (D-152) |
| `protocolReleases.file` | in the approach's repository: the file of the entries of its releases, `releases.md`; every entry needs its annotated tag on a release commit whose parent is its verified commit and that changes only this file, and every tag `v*` but `v0.1` needs an entry (D-109) |
| `releases.tool` | the directory of the tool a release runs with, read from the configuration at the release's commit; when it is not set, the pin's own directory, where a copy of the tool keeps its pin. `--product` and `--verify` run the `ont-check.mjs` of that directory at that commit, and say so; a commit without it, its pin or a suite's directory cannot be run, and says what it lacks (D-142) |
| `releases.dir`, `releases.pin` | a product's records of releases (`Version:`) and of deployments (`Release:`), one file each, a release's named by its version, `1.0.0.md`, a deployment's any other name, a record never written over a file (D-127), and the pin of the protocol whose SHA-256 at the commit a release records, the pin read at the path this key has in the configuration at that commit; the check finds each record intact or names what is wrong, and a deployment of a release with no record (D-111) |
| `taskRecords.dir` | directory of a task's records, one file each, each written by a writer of the tool with its seal (D-167): done (`Record: done`, `done.mjs`), the owner's approval of a version and his answer to a gate (`Record: approval`, `Kind: approval` or `gate`, `approve.mjs` from the registry, D-170), a snapshot of spend (`Record: spend-snapshot`, `round.mjs record`, D-169), the tests of the fixes of a round (`Record: fixes`, `round.mjs fixes`, D-168), a gate change (`Record: gate-change`, `gate-record.mjs change`, named `<time>-<task>-gate-change-<item>.md`) and a gate proof (`Record: gate-proof`, `gate-record.mjs proof`); the records of the executor's spend written before the logs (`Record: spend`) and the records without a seal written before seals start read as before; where `records.latinOnly` is set, a record of a gate change or of a gate proof is held to English and to paths of the repository, while a record of spend, of done or of approval is read as before (D-162); the check refuses a verdict of acceptance with no record of done behind it and a contribution recorded twice over intervals that overlap (D-107, D-108) |
| `mergeGate.paths` | the gate paths, from the root of the repository: a path ending in `/` names everything under it, `*` any name within one part; the guard of `merge-gate.mjs` refuses a change of one without a record of a gate change (D-165) |
| `mergeGate.rules` | the rule file: the ruleset of main as the GitHub API takes it and the permissions of Actions, which `merge-gate.mjs ruleset` prints (D-165) |
| `ci.workflow` | the workflow file of the project's full check in CI; the check reports a configuration without it, and fails when the file is missing (D-165) |

## Formats it expects

- **Definition rows:** ``| Kind | `class.name` | Term | Definition |``, anywhere in the ontology. A table is a run of consecutive table lines; the Kind cell holds no backticks. Together the rows are the glossary.
- **Type cells:** a fifth column, ``| Kind | `id` | Term | Type | Definition |``. Vocabulary: `text`, `number`, `boolean`, `integer` with optional bounds (`integer 0..2`, `integer 1..`), `date`, `datetime`, `one of a, b, c`, ``ref `ent.x` ``, ``refs `ent.x` ``, each optionally followed by `optional`.
- **Retired IDs:** ``| `old.id` | `new.id` | D-nn |`` under `headings.retired`; a dash instead of the new ID for a removed concept.
- **IDs in Markdown text:** in backticks; other text is not read as IDs. Doc anchors and test tags, below, have their own forms.
- **Implementation rows:** ``| `class.name` | `path`, `path` | note |`` inside the implementation section. Concepts realised in the same files may share a row: ``| `class.a`, `class.b` | `path` | |``.
- **Known divergences:** bullets under a heading that starts with `headings.divergences`, by default `### Known divergences`, each naming the concepts involved in backticks; the check fails on a line that names none. `--gap` prints them. With a ticket it prints only those naming its concepts: a line that names only concepts of the slice keeps it open, and one that also names other concepts is shown apart and not counted.
- **Mockup:** `data-ont="class.name"` attributes, and IDs in single quotes inside scripts (`'view.catalog'`). IDs built from templates are declared in a comment `/* data-ont dynamic: 'class.a','class.b' */`, and the markup must contain `data-ont="class.${`.
- **Decision entries:** headings matched by `decisions.entry`.
- **Checks:** ``| `check.section.name` | `id`, `id` | GIVEN | WHEN | THEN | auto, judged, review or run | covers |``, the last cell optional: the axis values the check covers, `refusal` or `time: days later`. A line `- Cannot occur: `action.id` value — why` rules a value out for the concepts it names, or for every concept when it names none; a line without a value or without a reason after the dash fails. under `## Section` headings; the second part of the ID is the section's key: the code span in the heading (``## Préstamo `loan` ``), one span of lowercase letters, digits and hyphens, or else the heading's Latin letters and digits in lowercase, joined by hyphens. Each ontology section with definition rows needs a key of its own, and every catalogue section's key must name one of them.
- **Scenario files (older):** an `IDs:` line at the start of a line.
- **Test tags:** IDs in square brackets anywhere in a test file, normally at the start of a test title: `test("[check.loan.renew-while-held] …")`, or a concept for what is not a product check, `test("[field.loan.renewals] …")`. Only `check` and configured classes are read, so `[0]` or `[x.y]` is not a tag.
- **Tickets:** an `IDs:` or `Ontology IDs:` line, and a `Checks:` line with the checks of the slice in backticks. A check named elsewhere in a ticket must exist but is not part of the slice. Older tickets may have a `## Scenarios` section whose bullets read `- [id, id] GIVEN … WHEN … THEN …`.
- **Doc anchors:** `<!-- ont: id, id@stamp -->` in pages of a doc set, outside code blocks and inline code; IDs are concepts or checks, stamps are optional and written by `stamp-docs.mjs`.
- **Supersession:** an entry that replaces older ones names them on a line matched by `decisions.supersedes`, by default `- Supersedes: D-05, D-07`. The line of a tentative entry takes effect when the entry is accepted.
- **Decision status (guard):** an entry is accepted when one of its lines matches `decisions.accepted`, by default a `- Date:` line containing `Status: accepted`. The check lists the entries that are not, as waiting for the owner's answer.
- **Sources (guard):** a line matched by `decisions.source`, by default `- Source: call of 2026-10-24, 00:41`. Once any entry has one, the guard fails on an entry accepted since its base without one, new or accepted from tentative; when the first source is newer than the base, only entries numbered after it are asked.
- **Code names:** `ont: id, id` in a comment of the code that implements the concepts, `// ont: rule.renewal`, in the files of the implementation table and of the directories under `code`. A stamp after `@` is ignored, so a doc anchor in such a file names its concepts too, and may name checks of the catalogue. Only the IDs after the marker are read, so a property path in code that looks like an ID is not one, and each must resolve, whatever its class. The marker is read as text, in any comment syntax and inside a string too; in Markdown, code blocks and inline code are examples and are not read.
- **Agent instructions:** IDs in backticks, of the project's ontology or of the approach, and entries of the project's log by the pattern of `decisions.ref`. In them `D-nn` is always an entry of the project's log; a rule of the approach is named by its ID. The project's retired IDs come first, and file names such as `action.yml` are not IDs.
- **Process entries:** `- Layer: process`, and `- Extends:` or `- Overrides:` with the IDs of the rules of the approach in backticks. Every such line is checked, and an empty one fails; a superseded entry may name a rule the approach has retired since.
- **Deferrals:** a line matched by `decisions.returnWhen`, by default `- Return when: a second branch opens`. The check lists every accepted deferral in force with its condition, as information.

## Hooks

Run the check on commits that touch any file it reads, the code paths that implement concepts among them: it reads their `ont:` names, and a change there is a reminder to update the implementation table. Run the guard with `--staged` on every commit, and in CI with `--base` set to the commit before the push or the base of the pull request. This repository's own hooks are `.githooks/pre-commit` and `.githooks/post-merge`, which rewrites the ontology tree after a merge into main where a clone sets `ont.treeOut`, and, there, says so, with the command that restores it, when the generator or a file it imports is missing from the working tree; on another branch or without a place it says nothing and runs nothing; Git runs `post-merge` only when `git merge` or `git pull` itself makes the merge commit or the fast-forward, so not after `git merge --continue`, a `git merge --no-commit` committed apart, or a real rebase: after those, run `node tools/ont-check/gen-tree.mjs --refresh` on main; and its CI is the two required checks of the merge gate, `.github/workflows/ont-check.yml` and `.github/workflows/ont-gate-guard.yml` (D-165); enable the hooks with `git config core.hooksPath .githooks`.
