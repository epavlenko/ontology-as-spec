# 7. Agent rules

<!-- ont: ent.agent-rules@99af23 -->

## What it is

A section in the repository's agent instructions (`AGENTS.md` or its equivalent) that tells any agent how to keep meaning current. It has two parts: a table of what else to update when something changes, and a short list of rules the check cannot enforce.

| You changed                                        | Also update                                                                                                                                        | Verify                          |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| A concept, rule, invariant or view in the ontology | run `format-ontology.mjs`; regenerate the tooltips; a revision history line; a decision entry when the reason is new                               | the check                       |
| A rule, invariant, hook or action in the ontology  | its check in the catalogue, before the code                                                                                                        | the check                       |
| The mockup                                         | the ontology first; `data-ont` on every new meaningful element and its map row                                                                     | the check, a browser smoke test |
| Code                                               | the rows and checks it implements first; an `ont:` comment naming the concepts the code implements; the implementation table and known divergences | the check, the tests            |
| A change about to be merged                        | `ont-check --review <base>`; an agent of another provider that did not write it gives each listed check a verdict with the change-review skill     | the reviewer's verdicts         |
| Your mind about an earlier decision                | a new dated entry that supersedes the old one                                                                                                      | the check                       |
| A concept becomes implemented                      | tests that implement its automatic checks, titled with the check IDs                                                                               | the check, the tests            |
| A definition row that a help page explains         | reread the sections the check lists, then `stamp-docs.mjs`; regenerate the reference pages                                                         | the check                       |

Generated files are never edited by hand; the check compares them with what the generators write.

Rules the check cannot enforce:

- A change of behavior starts in the ontology, its rows or its checks; the code and its tests are written from it after (`rule.ontology-changes-first`). The code, the mockup included, is written from the ontology: what it would do that the ontology does not say, including what an element deliberately does not do, is a gap in the ontology, so add the row or the check, or ask, before writing it (`rule.ontology-is-source`, `rule.behavior-in-ontology`, `rule.limits-in-ontology`).
- IDs are permanent. Renaming a term changes its row's text, never its ID. An ID that has to change goes under "Retired IDs" with its replacement; only the decision log keeps using it (`inv.ids-permanent`, `action.change-id`).
- Removing a concept is a decision: write the entry and retire the ID; the check then finds every reference left (`action.remove-concept`).
- The ontology describes the target. When the code disagrees, record the divergence; do not silently change either side (`rule.divergence-becomes-work`).
- Code that implements a concept names its ID next to it in a comment, `// ont: rule.renewal` (`rule.code-names-concepts`).
- What a partial implementation leaves out is a target concept, named in the note of its row. A note alone hides the work from `--gap` (`rule.partial-noted`).
- A choice the owner has not explicitly approved, such as a value you picked when asked to tune something, is recorded as tentative; the owner's approval accepts it (`rule.unconfirmed-tentative`).
- A question you can recommend an answer to is a tentative entry, not a line under open questions: your recommendation is its decision, the other options are rejected. The entry gives you no permission to act on the recommendation; your task or the owner does. When the owner answers, the entry names the answer on its `Source:` line (`rule.question-as-tentative`, `action.answer-tentative`).
- Name where a decision was made on its `Source:` line. When sources disagree, follow the owner's latest word; an answer someone gave for the owner keeps the entry tentative (`rule.source-precedence`).
- What you put off outside any slice gets an entry with a `Return when:` line, not a note that nobody will read again (`rule.deferral-returns`).
- A number is held as its role needs. A rule's value or a requirement is held by a check. A model's assumptions are held by a snapshot of its base scenario, each change of them is a short entry about its topic, and no check requires the model to reach its goal (`rule.number-by-role`, `rule.chosen-value-checked`).
- A consistency review reports what would mislead a reader or an agent, or would break a check. Style, the completeness of lists and compliance that changes nothing are not findings (`rule.findings-mislead`).
- Every change ends with a commit of its own files, never another agent's (`rule.commit-finished-work`).
- A rule here that comes from a rule of the approach or from a decision names it, by ID or entry; a rule that departs from the approach cites the process entry of the log that decided it (`rule.agent-rule-source`, `rule.departure-by-entry`).

## Why a table

Agents follow explicit procedures well and infer side effects badly. "Remember to keep docs in sync" produces nothing. "You changed the mockup, so add the map row and run this command" produces the map row. The table turns the dependency graph between artifacts into instructions, and the Verify column turns each instruction into something checkable.

The list after the table holds only the rules no check enforces; it exists because some rules have no mechanical check yet. Writing them down is the fallback. When a rule keeps being broken, it should move from the list into the check. Encoding a lesson in structure beats repeating it in prose.

The same order applies to every correction of an agent (`rule.strongest-step`). A mistake an agent made once it will make again, so the correction is held at the strongest step that can hold it. First the structure of the code, so the mistake cannot be written: a type, a boundary in the import graph, a single way to do a thing. Then a check of the tool, a test or a lint, which fail the build. Then a rule in the agent instructions, which an agent may not read. Last, what a reviewer remembers, which does not scale with the number of changes. A rule in the instructions is the fallback for what nothing else can hold, and the list after the table is where it goes. The order follows Lauren Tan's account of how a team of agents keeps a codebase trustworthy at hundreds of changes a day ([talk, 2026-09-21](https://x.com/poteto/status/2102050467505430555)).

## Reference

The rules for the section itself are in the reference: [Agent rules](../reference.md#agent-rules). Keep it short, because it is read at the start of every session and long sections are skimmed. Let every row name a path or a command. Let every task start by naming the IDs it touches: if an agent cannot name them, the task is not about meaning, or the ontology is incomplete. The tool enforces none of this directly; it enforces the consequences, because a skipped row usually fails the check. The same restraint applies to reviews: a consistency review reports what would mislead someone or break a check, not every imperfection it can find. And every change ends with a commit, since the guard protects only accepted entries that are in a commit, and a commit keeps each step easy to undo. The commit holds only the change's own files, since other agents may work in the same checkout. Who approves a commit or a push, and when to push, the approach leaves to the user; a project that does not let agents commit writes that as a process entry, as the next section shows.

## Where a rule comes from

A project's ontology is about its product. How its agents work is described by the approach's own ontology: the rules of this part and of the decision log are concepts of the approach, with IDs like any product's. So a process rule in a project's agent instructions, one that says how agents work rather than what the product is, names where it comes from: the rule of the approach it follows, by ID, or the entry of the project's log that decided it.

```markdown
- Every change ends with a commit of its own files (`rule.commit-finished-work`).
```

In the instructions, `D-nn` always means an entry of the project's own log; a rule of the approach is cited by its ID, never by the approach's entry numbers. The files stay prose, and commands and matters of style name nothing.

A project may depart from a rule of the approach, more strictly or more loosely, but only by an entry of its log that says so. A `Layer: process` line marks the entry as one about how agents work, and an `Extends:` or `Overrides:` line names the rule; the instruction that departs cites the entry. In one project that uses the approach, the agent instructions said by default not to commit and not to open a pull request. That narrowed `rule.commit-finished-work`, and nothing said so: an agent that knew the approach could not tell whether the project meant it, or why. Written as a departure, it is an entry:

```markdown
### D-63 · Agents leave commits and pull requests to the owner

- Date: 2026-10-27 · Status: accepted
- Source: the owner's message of 2026-10-27
- Layer: process
- Overrides: `rule.commit-finished-work`
- Decision: agents do not commit or open a pull request unless the task asks; a finished task ends with a list of the accepted entries that are not protected yet.
- Why: …
```

and an instruction that cites it:

```markdown
- Do not commit or open a pull request unless the task asks; say which accepted entries are not protected yet (`rule.commit-finished-work`, overridden by D-63).
```

The configuration lists the instruction files under `agentInstructions`. The check fails on a concept ID they mention that neither the project's ontology nor the approach defines, or that is retired, and on an entry they cite that the log does not have or that a later entry supersedes. It also fails on an entry with an `Extends:` or `Overrides:` line that lacks `Layer: process`, or on such a line that is empty or names something the approach does not define; while the entry is in force, a rule the approach has retired fails too, and a superseded entry, which is history, may still name one. A retired ID of the project stays retired where the approach has the same ID, and file names such as `action.yml` are not read as IDs. The approach's IDs travel with the tool, in `tools/ont-check/approach.json`, which the approach generates from its own ontology; a project copies it with the other files of the tool.

What the tool cannot tell is which lines are process rules, and whether a rule written in prose is stricter or looser than the approach. A reviewer reads the instructions for that: a process rule that names no source is a finding, and so is a departure without an entry.

## An independent critic

Before a change is merged, an agent of another provider that did not write it reviews it. Two agents of the same provider tend to share blind spots, and a reviewer handed the author's conclusions tends to confirm them, so the critic gets the diff and the IDs it touches, not the author's summary.

`ont-check --review <base>` gives the critic its checks, in two lists, the checks of review, which it gives a verdict reading the change, and the checks of run, which it carries out on the working product or has carried out (D-165): the project's checks whose concepts the change touches, through a changed definition row, a changed check, a changed file that names the concept in `ont:` or is in its implementation row, a changed doc section anchored to it or a changed ticket that lists it, or a changed file under a directory the configuration names under `reviewPaths`, which data files without `ont:` names need, and a check of run also when a changed section of its run guide names it; and the approach's checks for the kinds of artifact the change touches, such as the Decision section when the decision log changed, or the checks of run of the mockup when the mockup changed. The approach's checks of review and of run travel with the tool, each check of run with its section of the [run guide](../run-guide.md), which `--review` prints with a link at the commit the copy came from; when the copy of the tool is updated, the approach's checks of run whose guide changed are listed too. Until a later step of the approach, a check of run gets its verdict in the critic's table like any other: the critic carries it out by its guide, or gives not run with the reason. The critic follows the [change-review skill](../../skills/change-review/SKILL.md) and gives each check a verdict: pass, fail, not run when the check applies but could not be carried out, such as one that needs the running product, or not applicable, each with its evidence or reason. A check that could not be run is never written off as not applicable. A fail, or a finding of the change that remains, stops the merge; a not run with its reason does not stop it on its own (D-165). A verdict counts while the check's stamp is the one it was given at and the later commits change none of the files the critic read for it; a check whose case, concepts or files changed gets a new verdict, the check of errors and security reads every new diff, and the others stand (D-165). In the range of fixes after the narrow round that follows a confirmed condition, what counts is what `rule.fixes-held-by-tests` says instead, [below](#after-the-narrow-round): a fail or a finding of the usual path of the one issue of verdicts on the diff of the fixes stops no merge once fixed with a test, the verdicts of that issue count though the files they read change by those fixes, and the check of errors and security reads the diff of the fixes once, in that issue (D-164, D-165). The approach's checks of a judge and of the screens come only when the change touches a judge, a judged check, a view or a screen, or a file the configuration does not describe (D-98). For a change of code the critic also gets the approach's check of errors and security: it reads the diff for errors of correctness, secrets, unchecked input, wider access and flawed dependencies, and fails the check on any of them ([profile Code](../profiles.md#code)).

## Rounds of review

A review goes in rounds: the critic reports, the author fixes, the critic reads again. A step of review has no ceiling of rounds, and the approach no number of them: the rounds go on while each finds fewer important classes of findings of the change than the one before, two findings of one class counting once (D-152). A critic who finds a problem looks for it across its whole class, not only where it showed, so that the next round does not find its neighbour.

What follows a round: the next action of a round is the line `NEXT <task>:` of `--task` and `--rounds`, given by the ordered branches of [`derived.next-round`](../../ontology.md) and the one end of a step defined there; this guide does not restate them (D-164). The budget is no branch of a step: the task's next action, below, alone orders it. A verdict a narrow round does not read again is carried from the earlier round (D-165). The review of the result goes on only under an approval in force: when a later round of the statement withdraws it, the owner's approval too, `--rounds` says, as `--task` does, that work is not allowed.

Before any fix, the executor triages every finding of the round, important or nit: usual path, when it breaks the goal's condition on the usual path, or a rare history. A finding is usual path only when the executor names the concrete step of usual work it breaks; otherwise it is a rare history; he writes the step named in the notes of the round's record next to the finding, and the tool does not read it ("1028 a"). The reviewer marks each finding `usual` or `rare` as advice; the executor decides, either way, and writes the weight and the filing on the finding's line of the record he commits, which is what the tool reads. A rare history is filed, `limitation` or `later`, in the commit of the round's record, with no new record of done and no new round; filed findings count neither in the comparison nor in stagnation, so a change of design follows from the usual path alone (`rule.executor-triage`, D-164). A finding of acceptance is never filed, and a nit is fixed or filed like any other.

The reviewer of a result writes `Condition: holds` or `Condition: not yet` in every reply: whether the goal's condition by the approved statement is met. The executor carries `holds` into the round's record (`field.review-round.condition`). The reviewer of a round after another reads the fixes, the executor's marks, kept fixable ones too, and the filings ("1020 b").

Stagnation is the sign that patching does not converge: the last round has an important finding, and either an important class of it was an important finding of an earlier round of the step, or it found no fewer important classes than the round before it. Only important findings count, on both sides, so two rounds of nits are no stagnation, a class that was a nit before is no repeat, and an important finding after a round of nits only is more important classes than none, which is stagnation. The rounds compared are those after the last end of the step, a clean round of the statement, a clean round of the result whose acceptance held, judged for the version that round read and never against a later statement, or the owner's last approval; one function gives this for `--task`, `--rounds` and the check, so they name one next action; the first round with findings after it is not stagnation. On stagnation the author changes the design of the solution rather than patching it, except after the one round that follows a confirmed condition, after which no round follows ([below](#after-the-narrow-round)); the tool cannot tell a new design from a patch, so the reviewer of the next round judges it.

`not fixable` means that the finding cannot be fixed without changing what the owner decided, an item of the approved statement with its source or his answer; it goes to him, and `--task` then names that question alone. The gate holds the whole task, not only the round after it: a later clean round, even a clean acceptance or a reviewer's clean round that approves another version, does not close it, and `done.mjs` refuses while it is open. His answer is a new version of the statement with his approval, after which the rounds before it are not read and the next round takes the next free number. A rare history is filed in `docs/limitations.md` with the value `limitation` only when it is what the approach does not do by choice, and a fault of the tool or a finding outside the statement in a ticket under `issues/` with `later` ("1021 b"); the file must hold the finding's class, and a filed finding neither makes its round unclean nor counts in the comparison. In a verdict of acceptance a filed finding is an error: an item of the approved statement that is not met is not put off. Whether a finding belongs where it was filed is the executor's decision; the tool does not see it, and the reviewer of the next round, if there is one, may name a wrong filing as a finding (`rule.findings-filed`).

The end of the step of the review of the result makes the change ready to merge; without a verdict of acceptance that holds the step has not ended, and after the narrow round that follows a confirmed condition it ends either with that narrow round, when it has no finding of the change and its verdict of acceptance holds, and the change is merged at once, or, after a narrow round with findings, with the record of done after the fixes that ends the range of fixes (D-164). Whether it is merged or published is the owner's policy; the approach asks that it is followed and does not set it. The owner is asked only at his gates, which `derived.next-round` names, and when the budget with its reserve is exhausted.

## After the narrow round

Once the reviewer of the result has confirmed the goal's condition and the narrow round that follows the confirmation has not ended the step, no round of review and no question to the owner follow it; the owner is asked only on a finding `not fixable` and on a spent budget ("1020 b", D-164). `--task` names one next action. A clean narrow round, its verdict of acceptance holding and no finding of the change in it, ends the step: the change is merged at once, with no fixes, no issue of verdicts and no new record of done. When the narrow round has no verdict of acceptance, or one the tool refuses, as one of another commit, its reviewer gives the verdict again on the same result; it is recorded after the narrow round with the next narrow number and read as the narrow round's, and it is no new round. Otherwise the executor fixes each finding of the usual path of the narrow round, a finding of its acceptance too, and closes each by a test; a finding of the usual path is never filed, and a rare one is filed as the triage above says. Then a reviewer of another provider gives one issue of verdicts on the diff of the fixes, `ont-check --review <the narrow round's commit> --record <table>`, which `--review` names as that issue and which is no round: the check of errors in code is given once there, its verdicts count for the merge though the files they read changed after, and a stamp that a fix changed does not make them stop being current. The findings of that issue, its fails and those its reviewer reports, are fixed with a test with no new issue when they are of the usual path, and filed when they are rare. Then `done.mjs` records done on the last commit of the fixes, and the change is merged within the owner's gates; a clean narrow round is merged as it is (D-165).

The commits between the narrow round's commit and that record of done are the range of fixes (`rule.fixes-held-by-tests`). One function of the tool gives it from the records that exist, the narrow round's `Commits:` and the record of done's `Commit:`, and ends it at the head of the working copy, for `done.mjs` the commit it records done on, while there is no such record of done; `--task`, `--rounds`, `done.mjs`, `--review`, the check's current records and `merge-gate.mjs records-only` ask it alike. Before the merge, records-only compares the head, outside `reviews/`, after a clean narrow round, which no fixes and no record of done follow, with the commit that round reviewed, the one the reviewer checked, merged with main, and after a narrow round with findings with the commit of the record of done that ends the range, merged with main too; never with the head; a commit after the record of done is outside the range, and a change in it is refused as any change no reviewer read. A record of a gate change still names the last commit of the pull request outside `reviews/`. Whether the issue was given and whether each fix has a test of its own the tool does not see yet ([limitations](../limitations.md)).

## What a review costs and finds

With `reviewRounds` in the configuration, every round is a file of its own: the task, the step, the round's number and whether it was narrow, the commits, the reviewer, the tokens that are known, how many checks were listed, given and carried, and a line for each finding with its class, its weight, whether it is of the change, whether it is fixable, not fixable or filed as `limitation` or `later`, and the test that holds its fix or the file it is filed in, and on a review of the result `Condition: holds` when the reviewer confirmed the goal's condition (D-99, D-152, D-164). A line `Ceiling:` of an older record is read and decides nothing. The record is read by one grammar: its head, up to a heading line `## `, is the fields, each once, then at most one block `Findings:`, then at most one verdict of acceptance, each block only of finding lines directly under its name; any other line, a second block, a field after the blocks or a line starting with # that is not `## ` makes the record unreadable, naming the line, and so does a line `Statement-hash:` left blank, or missing from a round of either step at or after `reviewRounds.gatesFrom`, since a round that names no version would drop out of the review of its version unseen. The reviewer's notes go after the heading, and the tool does not read them. A record that cannot be read, of any task or of none, blocks every task: `--task` and `--rounds` name its correction as the one next action, and `done.mjs` refuses to record done, so that a dropped record never leaves an older approval in force. `ont-check --rounds` says what follows the last round of each task, with the task's budget by the limits of the version approved now, read from that version's latest record of done since `--rounds` takes no statement file, and by the configuration's limits only when no record gives them (D-164, D-152), by the function `--task` uses, so that a verdict of acceptance the check refuses ends no step in either (D-164), and once a step has ten applications, one step of one task with its rounds together, what it cost and found. A step whose applications found nothing is a candidate to simplify; the owner decides, and nothing is removed by the tool.

The verdicts themselves are verdict records. The critic gives a table of them, and `ont-check --review <base> --record <table>` writes one record for each new verdict, each pass or fail with its `Performer:`, `agent` unless the row names another, and none for a carried one (D-165), and refuses the table when a check is missing, unknown, given twice, carried at another stamp or over files that changed since, or is the check of errors in code, which reads every new diff (D-100).

## A task's statement and its approval

A task starts from its statement, written before work: the owner's sources for it, what to do and what not to do, its condition of done as commands and its budget; it sets no ceiling of rounds. It may live outside the repository, since it holds the owner's words; the tool reads only its lines `Done-when:`, `Budget-new-input:`, `Budget-output:` and `Budget-reserve:`, and names its version by the SHA-256 of the file (D-152).

The statement is reviewed in rounds like a change, and each round records the hash of the version it read on a line `Statement-hash:`. An approval is in force for a version when the last round of the review of the statement, by its time, is clean and read that version, or when the last of those rounds and the owner's approvals is his approval of that version (D-121, below); the approval in force at a moment is decided by the last of them before it (D-164). The same criterion lets the executor start and lets a reviewer accept the result; a later round of a new version that finds something withdraws the approval of the old one too. When the statement is edited after a clean round or the owner's approval, the next is a full round of the new version, with the next free number of the full rounds over every version, however many rounds came before; no round is counted. A next round of either kind takes the next free number of its kind, and numbers never repeat between versions.

`ont-check --task <task> --statement <file>` prints the state of the statement, of the result, of the record of done and of the budget, each a state only, and then the task's one next action, once, on a line `NEXT`. That action is the first that holds of these branches, in this order: (1) unreadable record: correct a record of rounds that cannot be read, a blank or missing `Statement-hash:` among them, or move or remove a late record; (2) done: within the current version window, the last round of the result ends its step, as the end of a step above says, or the record of done after the narrow round ends the range of fixes ([below](#after-the-narrow-round)), and the file given is the window's version; the change is merged; (3) budget question: a spent budget, records of spend that overlap, a line of the budget that cannot be read or an approved file with no command of done (`Done-when:`) is the question to the owner, ahead of an open gate; (4) open gate: a finding `not fixable` after the owner's last approval is the question to him; (5) no review: the statement needs a review; (6) under review: the next round of the statement's review; (7) no version: give the file; (8) changed: a full round of the changed statement; (9) step: with no round of the result in the window, the executor works under its version and records done, or, once that record of done is there, the first full round of the review of the result, with the next free number; otherwise the next round of the result. Three rules make every reader agree whatever version a record names, and they are stated here once (D-152). First, the open gates are read over the whole task: a finding `not fixable` in any round of either step after the owner's last approval, whatever version the round names, holds until his newer approval, and a reviewer's clean round, of the statement or of the result, never clears it. Second, a late record is refused, not read: a round of the result, with its verdict of acceptance, or a record of done that names another version than the one last approved when it ended, or none, and ends after that version's approval, cannot be read; it blocks every task in `--task`, `--rounds`, `done.mjs` and the check, and the executor moves it out of the records or removes it. Third, a round of either step at or after `reviewRounds.gatesFrom`, or any round when the key is not set, gives its `Statement-hash:`: one without it is malformed by the grammar, a fact of the record alone, so it blocks every task and no later approval hides it; an older round reads as it did. Within these rules every other reader, each branch, the acceptance, the round that ends the task and its commits, the lines of `--task`, the overspend the check compares and `done.mjs`, reads the window of the current version by one task view. The current version is the version approved now, or, while a later round withdraws its approval, the version last approved; its window starts at the first of the events at the end of the history that approve it, a clean round of the statement or the owner's approval, and the rounds of the result and records of done after that time are the window's. The rounds and records of done of an earlier window count only for the numbers of rounds and for the budget; `--task` lists them on a line `TASK <task> · not read`, and a record of done made before the version's approval was withdrawn and given again is not reused. `--rounds` prints, for every task any record names, a round or a record of spend, of done or of approval, the counts of its rounds by step and then the lines of `--task` given no file, from the same function, so its states and its `NEXT` line are `--task`'s, and `done.mjs` asks it for new work and records done only on an action of kind work: each action carries its kind, set where it is decided, work, review, question, correct or done, and a question of the step, as a legacy finding `not fixable` in the last round of the result, is of kind question, so a spent budget refuses a fresh record of done after the task is done too; all three read the records by one function and give one action from the same records. One exception: `--rounds`, which reads no statement, measures the budget by the limits of the version in force as a record of that version holds them, its kept brief, its record of done or its snapshot of spend, and by the configuration's only when none does, while `--task` measures it by the statement's, so for a version approved before any record of it holds its limits the two may differ on the budget question alone (D-174, [ticket 8](../../issues/0008-budget-stops-without-measured-spend.md)). Two questions are kept apart. How a record is read is decided by its time alone: a round, a record of done or of approval before the configuration's `reviewRounds.gatesFrom` is legacy and reads as it did, never late, its `not fixable` opening no gate; every record at or after the time follows the three rules. Whether a task follows the approval of versions above, branches 5 to 8, is decided by its records, never by the time: once any record of it names a version, a round with `Statement-hash:`, a record of done or of the owner's approval, it does, so a task versioned before the time still needs its file and an approval in force, and a round of the result that names a version with no approval in force is followed by the review of the statement in `--task`, `--rounds` and `done.mjs`, never by a round of the result; only a task none of whose records names a version, as one recorded before D-106, skips branches 5 to 8, and by the third rule all its records are before the time. `done.mjs` asks for that action before any refusal of its own and refuses with its text, so with no approval in force a spent budget or an open gate is its refusal too. The state of the result calls the last round's clean verdict of acceptance refused, with why, when it does not hold for the window's latest record of done. A finding `not fixable` written before the configuration's `reviewRounds.gatesFrom` carries its earlier meaning, not fixable within the task, and opens no gate; this repository sets it to the time of the first record of done of task round-rules, the start of the review of the first result under D-152.

## The owner's approval

When a finding of the review of a statement goes to the owner, as one `not fixable` does, he may approve a version himself, or answer the gate of a round. The executor writes his answer with `approve.mjs <task> --statement <file> --question <N> --kind approval` or `--kind gate --round <file of the round>`, `--english <file>` giving the English translation of his words: it reads the answer from the registry of questions by the command the environment names in `ONT_REGISTRY_CMD`, and writes nothing when the registry has no answer of his, when the question does not name the task and the version, or the round, or when the option he chose does not approve or does not answer the gate (D-170). The record is in the directory of `taskRecords`: `Record: approval`, its kind, the task, `Statement-hash:` of the version, `By: owner`, the question, `Source:` with the question, the date, the option and his words translated, and the time in UTC, sealed. It counts beside the rounds: the last by time of the rounds of the statement and the owner's approvals decides, so his approval lets work start and a result be accepted, and a later round with findings withdraws it. A record without a source, or by anyone but the owner, cannot be read: the check fails and nothing is approved.

## Acceptance after done

When the executor is done, `done.mjs <task> --statement <file>` runs the statement's commands of done on the commit in a temporary worktree and, under an approval in force for that version and only when every command passed, writes the record of done in the directory of `taskRecords`: the task, the commit, the hash of the statement, the statement's limits and reserve as its lines `Budget-new-input:`, `Budget-output:` and `Budget-reserve:` give them, or `none`, the time the commands had run, to the second in UTC, and each command with its result (D-152, D-147). What the statement asks the record of done to name besides the commands, such as each row of the catalogue the task changed, goes in a file given with `--evidence FILE`, whose lines go under a line `Evidence:` after the checks, where the reviewer of acceptance reads them; where `records.latinOnly` is set they hold English text and paths of the repository only, or nothing is written (D-166).

Then a reviewer checks the result against the approved version: every item of what to do and of done when, and the owner's sources. The verdict of acceptance is written in the same round of the review of the result, beside the verdict on merging, as `Acceptance: clean` or as `Acceptance:` with a finding line for each item the result does not meet. The round is clean only when both have no finding of the change. The round names the commit it reviewed on its line `Commits:`, the last of a range. The check refuses a verdict of acceptance with no record of done, given before the record was made, after a record with a failed check, for another version of the statement, after a record of done made with no approval in force for its version or of another commit than the one the round reviewed, or when the approval was withdrawn before the acceptance; with the statement's file, `--task` also refuses it when the file is no longer that version or when the record of done ran other commands than the file's lines `Done-when:`, exactly and in their order, and says done only for an acceptance that holds (D-164). The acceptance must be of the latest record of done of the window: after a new record of done of that version for a newer commit, `--task` and `--rounds` say the task is not done until a round accepts it, and `--task` names the latest record on a line of its own (D-164). Every commit a record names is tested in the repository by one test, `git cat-file -e`, and a missing one is an error only where what the record proves rests on it: a record of done whose commit is not there cannot be read and binds no acceptance, so the task is not done; the round that would end the task, the last round of the review of its result in the window, clean on merging and in its acceptance, whose acceptance holds for the latest record of done, an entry of `releases.md` and a record of a product release whose commit is not there are errors of the check. One function names that round, so the check, `--task` and `--rounds` all refuse its acceptance for the missing commit, and none of them calls the task done (D-164). Every other round, such as one with a finding on merging or one a later round follows, and every manual run, that names a commit the clone does not have, as a clone made after a rewrite of the history may, is information, and the check passes. A branch named in `Commits:` is not held to it, since it may be deleted after the round (D-145). After the narrow round that follows a confirmed condition, the acceptance of the result is that round's verdict of acceptance, held by these rules as the records were when it was given, together with the record of done after the fixes, with no new acceptance ([below](#after-the-narrow-round)). An acceptance by the owner that his policy asks for, as before a publication, stays his.

## Records written by the tool

Every record of the process is written by a writer of the tool, never by hand, and carries its seal on its first line, `Seal: v1 <sha256>`, the hash of the rest of the file after the prefix of its format (D-167). Where the configuration at the base of a pull request sets `records.sealsFrom`, the guard `ont-gate-guard` refuses a record the pull request adds after the merge that brought the key without a seal that is its text's, `SEAL_MISSING` or `SEAL_WRONG`, and always refuses a record of the base, or one an earlier commit of the pull request added, that is changed or removed, `RECORD_CHANGED` or `RECORD_REMOVED`; a correction is a new record. The full check and pre-commit say the same as information. A seal does not stop a deliberate forgery ([limitations](../limitations.md)).

- **A round**, in two steps (D-168). Before it, `round.mjs brief <task> --step statement|result --statement <file>` gives the brief's lines, kept once in the Git directory of the working copy, only when the task's next action is that round: for the statement, once the file is corrected since the last round with findings; for the result, once a record of done newer than the last round is on a commit whose tree differs, the records of the rounds of the step and of done aside, or for the verdict of acceptance alone on the same result. The lines open the reviewer's brief, and the reviewer's reply begins with them word for word. After it, `round.mjs record <task> --from <reply> --triage <file>`, run in the same working copy with the same environment, writes the round from the reply the review skill asks for and the executor's triage, taking the scope of the budget and the task's limits as those of the brief's version, whose lines `Goal:`, `Budget-new-input:`, `Budget-output:` and `Budget-reserve:` the brief wrote from the statement, whatever version is approved in force, so that with no statement given a task of a goal keeps its goal, and the round of a statement, a first one or a revision reviewed while an earlier version is approved, writes its snapshot under its own version with that version's limits and reserve (D-172, D-174); one line for each finding, `<class> · usual path: <the step it breaks>`, `· not fixable`, `· limitation` or `· later: issues/NNNN.md`; it refuses a reply that differs from the brief, a finding with no triage and a finding of acceptance filed.
- **The tests of the fixes**: `round.mjs fixes <task> --round <file> --from <file>` writes, for each class of a fixable finding of the round, the test that holds it, `class · file · name`; the round's record stays as it was, and the next round reads the test from the record of fixes.
- **The verdicts**: `--review --record` (`Origin: review`); a run of a check of run outside a review, in two steps, `--run-start <check>` before it and `--run-record <check> --verdict … --performer … --by … --evidence …` after it, on one committed state (`Origin: run`), which `--review` carries while nothing outside the records changed since (D-171).
- **Done**: `done.mjs`. **The owner's approval and his answer to a gate**: `approve.mjs`, above.
- **The gate records** (D-170): `gate-record.mjs change <task> --statement <file> --clause <item> --paths <paths> --base <main>` on the last commit outside `reviews/`, one record for each item of What to do that allows a change of gate paths, and `--refresh` after any later commit outside `reviews/`; `gate-record.mjs proof <task> --gate <gate> --check <check> --pr <n> --kind refusal|pass --repo <owner>/<repo> --response <file>` after the merge, from the pull request and its runs.
- **Spend**: no record of it is written by hand. Where the configuration sets `spend.fromLogs`, the tool counts it from the session logs each time, by the unit of the goal the statement names on `Goal:`, and `round.mjs record` writes a snapshot of it with each round; the inputs come from the environment, `ONT_CLAUDE_LOGS`, `ONT_CODEX_LOGS`, `ONT_EXECUTOR_SESSIONS` and `ONT_GOAL_STATEMENT`, and a writer refuses without one it needs (D-169). ## The budget of a task

A project sets a task's default limits in its configuration, `budget.newInput` and `budget.output`, and the multiplier at which it stops, `budget.reserve`; a statement's own lines replace the limits and the reserve for its task, each that it gives, `Budget-reserve:` a number of 1 or more such as `1.5` (D-150). Limits belong to a version of the statement. One function gives the limits, the reserve and the goal of one version, and every reader asks it with the version that applies to what it reads (D-174): the version's own lines, from its file where the file given is that version, or else as a record of that version copies them, the task's kept brief that names it or its latest record of done of it, or else the latest snapshot of spend of the task that names it, which holds what its writer compared with; a record of another version gives none; each limit and the reserve the configuration's where none holds it or the version gives none. A round's writer asks for its brief's version, the text of an overspend for the version its round names, and `--task`, `--rounds`, the check and `done.mjs` for the version in force: that of the approval in force, or with none the file given, or else the version of the task's kept brief, or else the version its latest round names. `--task` compares with the file only a record of done of the file's version (D-147). A version approved before any record of it holds limits, as by the owner's approval of a version never reviewed by the tool's writers, gives the configuration's until its first brief, record of done or snapshot. The reserve is read in the same order from the same places as the limits; with limits and no reserve in the statement or the configuration the reserve is 1, and the tool says so; with no limit anywhere it says nothing of a budget. The approach sets no number (D-108).

The spend is the new input and the output of every contribution to the task, one run of a model each, named by its provider and its session or task there: the rounds of its review, which give `Contribution:` with `Start:`, and the executor's own records of spend (`Record: spend`, with a start and an end). Cached tokens are not summed. Two records of one contribution over intervals that overlap, even in part, or that begin in the same second, are an error, and so is a record that begins after it ends, which counts in no sum. While two records overlap, `--task` sums none of the spend and the next step is a question to the owner, until they are corrected (D-118); the pairs are those the check finds over the records of every task, so a session recorded in two tasks stops both (D-124). The output says for how many contributions the spend is known; the stop is decided by what is known, each value on its own.

The budget is checked when the next action is chosen, not after: run `--task` before every step of the executor and every round; a round of the result clean on merging with no verdict of acceptance yet is such a point too (D-164). When the budget with its reserve is exhausted, the next step or round is a question to the owner instead, ahead of the rules of convergence, and it is the one next action `--task` names: no line of it then lets work start or go on (D-124). A clean round that ends a step stays clean. A clean round of the review of the result, with acceptance clean, ends the task even past its budget: `--task` prints the overspend, the record of the round names it on a line `Overspend:`, exactly as the tool prints it, `new input N of L, output N of L`, each number written one way, a whole number or a decimal with a point, such as `151.5` for a limit of 101 with a reserve of 1.5; `--task` and the check refuse any other line, a missing one past the limit and one within it alike, by the same limits (D-164, D-147); and the executor reports it to the owner. A clean review of the statement ends no task, so a budget spent past it blocks the start of work.

The budget is the one hard stop. On the way to it, each run of `--task` prints a line `REPORT` with the marks the spend has passed, new input and output each on its own: `half` at half the limit or more, `limit` at the limit or more, the limit before the reserve; one contribution that passes both gives both. The line stands apart from the next action, which it does not change: work goes on below the reserve, the question comes past it, and a clean round of acceptance past it still ends the task. The executor sends the owner one report with every mark not yet reported. When the spend cannot be summed, because records of one contribution overlap, or a line of the statement's budget cannot be read, the next action is the question and no line `REPORT` is printed, since no spend is measured. How a limit comes from an estimate is the owner's rule, not the approach's (D-152).

### Spend from the session logs

Where the configuration sets `spend.fromLogs`, the spend above is not summed from records: `spend.mjs` counts it again from the session logs each time `--task`, `--rounds`, `round.mjs` or `done.mjs` asks, with nothing kept between (D-169). The unit of the budget is the goal a statement names on its line `Goal: <goal>`, whose tasks the configuration lists under `goals`, or else the task; a task the goal does not list is an error. The goal comes with the limits of the version that applies, from the same record, as [above](#the-budget-of-a-task): the brief, which `round.mjs brief` wrote with the statement's goal, limits and reserve, the record of done, which `done.mjs` wrote with them, or the snapshot of spend of that version (D-172, D-174). The unit starts at its first brief of a round, or, for rounds written before the writers, at its first round of the review of a statement. The spend of the unit is every event after the start in the executor's sessions, `ONT_EXECUTOR_SESSIONS`, and in the sessions whose first message names the unit or one of its tasks, each event once; the spend of a task of a goal is only the sessions whose first message names that task; the spend of a round is its reviewer's session from the brief to the next brief. The goal's limits and reserve come from its statement, `ONT_GOAL_STATEMENT`, whose version must be the one approved in force. `--task` names the question to the owner when the reserve of the goal or of the task is spent, and then `round.mjs brief` and `done.mjs` refuse; `--rounds` shows the sums and names no action by the budget; `round.mjs record` records a round already briefed as it is. Each round names the snapshot of spend written with it on `Spend-record:`, and `Overspend:` is written only on the round that ends the task with acceptance clean, from that snapshot, which the check, with no logs in CI, compares with it.

## How it fails in practice

- **The table describes an older layout of the repository.** When paths move, update the table in the same change. Include the agent instructions file in the paths that trigger the check.
- **Rules that should be checks stay rules forever.** Review the list from time to time and ask which item could be a check.
- **A correction goes into the instructions by habit.** The agent is told once more in prose, and the next agent repeats the mistake. Ask first whether the code, a check, a test or a lint can make it impossible.
- **Instructions that quietly differ from the approach.** A project's rule says less or more than the rule of the approach it replaces, and nothing records the choice. Write the departure as a process entry and cite it from the instruction.
- **Reviews that list everything.** A finding that misleads no one costs the reader's attention and teaches agents that the list is noise. Report what would mislead a reader or an agent, or would break a check, and leave style and completeness alone.
