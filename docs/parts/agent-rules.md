# 7. Agent rules

<!-- ont: ent.agent-rules@99af23 -->

## What it is

A section in the repository's agent instructions (`AGENTS.md` or its equivalent) that tells any agent how to keep meaning current. It has two parts: a table of what else to update when something changes, and a short list of rules the check cannot enforce.

| You changed                                        | Also update                                                                                                                                        | Verify                          |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| A concept, rule, invariant or view in the ontology | run `format-ontology.mjs`; regenerate the tooltips; a revision history line; a decision entry when the reason is new                               | the check                       |
| A rule, invariant, hook or action in the ontology  | its check in the catalogue, before the code                                                                                                        | the check                       |
| The mockup                                         | the ontology first; `data-ont` on every new meaningful element and its map row                                                                     | the check, a browser smoke test |
| Code                                               | the rows and checks it implements first; an `ont:` comment naming the concepts the code implements; the implementation table and known divergences | the check, the tests            |
| A change about to be merged                        | `ont-check --review <base>`; an agent of another provider that did not write it gives each listed check a verdict with the change-review skill     | the reviewer's verdicts         |
| Your mind about an earlier decision                | a new dated entry that supersedes the old one                                                                                                      | the check                       |
| A concept becomes implemented                      | tests that implement its automatic checks, titled with the check IDs                                                                               | the check, the tests            |
| A definition row that a help page explains         | reread the sections the check lists, then `stamp-docs.mjs`; regenerate the reference pages                                                         | the check                       |

Generated files are never edited by hand; the check compares them with what the generators write.

Rules the check cannot enforce:

- A change of behavior starts in the ontology, its rows or its checks; the code and its tests are written from it after (`rule.ontology-changes-first`). The code, the mockup included, is written from the ontology: what it would do that the ontology does not say, including what an element deliberately does not do, is a gap in the ontology, so add the row or the check, or ask, before writing it (`rule.ontology-is-source`, `rule.behavior-in-ontology`, `rule.limits-in-ontology`).
- IDs are permanent. Renaming a term changes its row's text, never its ID. An ID that has to change goes under "Retired IDs" with its replacement; only the decision log keeps using it (`inv.ids-permanent`, `action.change-id`).
- Removing a concept is a decision: write the entry and retire the ID; the check then finds every reference left (`action.remove-concept`).
- The ontology describes the target. When the code disagrees, record the divergence; do not silently change either side (`rule.divergence-becomes-work`).
- Code that implements a concept names its ID next to it in a comment, `// ont: rule.renewal` (`rule.code-names-concepts`).
- What a partial implementation leaves out is a target concept, named in the note of its row. A note alone hides the work from `--gap` (`rule.partial-noted`).
- A choice the owner has not explicitly approved, such as a value you picked when asked to tune something, is recorded as tentative; the owner's approval accepts it (`rule.unconfirmed-tentative`).
- A question you can recommend an answer to is a tentative entry, not a line under open questions: your recommendation is its decision, the other options are rejected. The entry gives you no permission to act on the recommendation; your task or the owner does. When the owner answers, the entry names the answer on its `Source:` line (`rule.question-as-tentative`, `action.answer-tentative`).
- Name where a decision was made on its `Source:` line. When sources disagree, follow the owner's latest word; an answer someone gave for the owner keeps the entry tentative (`rule.source-precedence`).
- What you put off outside any slice gets an entry with a `Return when:` line, not a note that nobody will read again (`rule.deferral-returns`).
- A number is held as its role needs. A rule's value or a requirement is held by a check. A model's assumptions are held by a snapshot of its base scenario, each change of them is a short entry about its topic, and no check requires the model to reach its goal (`rule.number-by-role`, `rule.chosen-value-checked`).
- A consistency review reports what would mislead a reader or an agent, or would break a check. Style, the completeness of lists and compliance that changes nothing are not findings (`rule.findings-mislead`).
- Every change ends with a commit of its own files, never another agent's (`rule.commit-finished-work`).
- A rule here that comes from a rule of the approach or from a decision names it, by ID or entry; a rule that departs from the approach cites the process entry of the log that decided it (`rule.agent-rule-source`, `rule.departure-by-entry`).

## Why a table

Agents follow explicit procedures well and infer side effects badly. "Remember to keep docs in sync" produces nothing. "You changed the mockup, so add the map row and run this command" produces the map row. The table turns the dependency graph between artifacts into instructions, and the Verify column turns each instruction into something checkable.

The list after the table holds only the rules no check enforces; it exists because some rules have no mechanical check yet. Writing them down is the fallback. When a rule keeps being broken, it should move from the list into the check. Encoding a lesson in structure beats repeating it in prose.

The same order applies to every correction of an agent (`rule.strongest-step`). A mistake an agent made once it will make again, so the correction is held at the strongest step that can hold it. First the structure of the code, so the mistake cannot be written: a type, a boundary in the import graph, a single way to do a thing. Then a check of the tool, a test or a lint, which fail the build. Then a rule in the agent instructions, which an agent may not read. Last, what a reviewer remembers, which does not scale with the number of changes. A rule in the instructions is the fallback for what nothing else can hold, and the list after the table is where it goes. The order follows Lauren Tan's account of how a team of agents keeps a codebase trustworthy at hundreds of changes a day ([talk, 2026-09-21](https://x.com/poteto/status/2102050467505430555)).

## Reference

The rules for the section itself are in the reference: [Agent rules](../reference.md#agent-rules). Keep it short, because it is read at the start of every session and long sections are skimmed. Let every row name a path or a command. Let every task start by naming the IDs it touches: if an agent cannot name them, the task is not about meaning, or the ontology is incomplete. The tool enforces none of this directly; it enforces the consequences, because a skipped row usually fails the check. The same restraint applies to reviews: a consistency review reports what would mislead someone or break a check, not every imperfection it can find. And every change ends with a commit, since the guard protects only accepted entries that are in a commit, and a commit keeps each step easy to undo. The commit holds only the change's own files, since other agents may work in the same checkout. Who approves a commit or a push, and when to push, the approach leaves to the user; a project that does not let agents commit writes that as a process entry, as the next section shows.

## Where a rule comes from

A project's ontology is about its product. How its agents work is described by the approach's own ontology: the rules of this part and of the decision log are concepts of the approach, with IDs like any product's. So a process rule in a project's agent instructions, one that says how agents work rather than what the product is, names where it comes from: the rule of the approach it follows, by ID, or the entry of the project's log that decided it.

```markdown
- Every change ends with a commit of its own files (`rule.commit-finished-work`).
```

In the instructions, `D-nn` always means an entry of the project's own log; a rule of the approach is cited by its ID, never by the approach's entry numbers. The files stay prose, and commands and matters of style name nothing.

A project may depart from a rule of the approach, more strictly or more loosely, but only by an entry of its log that says so. A `Layer: process` line marks the entry as one about how agents work, and an `Extends:` or `Overrides:` line names the rule; the instruction that departs cites the entry. In one project that uses the approach, the agent instructions said by default not to commit and not to open a pull request. That narrowed `rule.commit-finished-work`, and nothing said so: an agent that knew the approach could not tell whether the project meant it, or why. Written as a departure, it is an entry:

```markdown
### D-63 · Agents leave commits and pull requests to the owner

- Date: 2026-10-27 · Status: accepted
- Source: the owner's message of 2026-10-27
- Layer: process
- Overrides: `rule.commit-finished-work`
- Decision: agents do not commit or open a pull request unless the task asks; a finished task ends with a list of the accepted entries that are not protected yet.
- Why: …
```

and an instruction that cites it:

```markdown
- Do not commit or open a pull request unless the task asks; say which accepted entries are not protected yet (`rule.commit-finished-work`, overridden by D-63).
```

The configuration lists the instruction files under `agentInstructions`. The check fails on a concept ID they mention that neither the project's ontology nor the approach defines, or that is retired, and on an entry they cite that the log does not have or that a later entry supersedes. It also fails on an entry with an `Extends:` or `Overrides:` line that lacks `Layer: process`, or on such a line that is empty or names something the approach does not define; while the entry is in force, a rule the approach has retired fails too, and a superseded entry, which is history, may still name one. A retired ID of the project stays retired where the approach has the same ID, and file names such as `action.yml` are not read as IDs. The approach's IDs travel with the tool, in `tools/ont-check/approach.json`, which the approach generates from its own ontology; a project copies it with the other files of the tool.

What the tool cannot tell is which lines are process rules, and whether a rule written in prose is stricter or looser than the approach. A reviewer reads the instructions for that: a process rule that names no source is a finding, and so is a departure without an entry.

## An independent critic

Before a change is merged, an agent of another provider that did not write it reviews it. Two agents of the same provider tend to share blind spots, and a reviewer handed the author's conclusions tends to confirm them, so the critic gets the diff and the IDs it touches, not the author's summary.

`ont-check --review <base>` gives the critic its checks: the manual checks of the project whose concepts the change touches, through a changed definition row, a changed check, a changed file that names the concept in `ont:` or is in its implementation row, a changed doc section anchored to it or a changed ticket that lists it, or a changed file under a directory the configuration names under `reviewPaths`, which data files without `ont:` names need; and the manual checks of the approach for the kinds of artifact the change touches, such as the Decision section when the decision log changed. The approach's manual checks travel with the tool. The critic follows the [change-review skill](../../skills/change-review/SKILL.md) and gives each check a verdict: pass, fail, not run when the check applies but could not be carried out, such as one that needs the running product, or not applicable, each with its evidence or reason. A check that could not be run is never written off as not applicable. A fail, or a finding of the change that remains, stops the merge; a not run with its reason does not stop it on its own (D-94). A verdict counts while the check's stamp is the one it was given at and the later commits change none of the files the critic read for it; a check whose case, concepts or files changed gets a new verdict, the check of errors and security reads every new diff, and the others stand (D-95). The approach's checks of a judge and of the screens come only when the change touches a judge, a judged check, a view or a screen, or a file the configuration does not describe (D-98). For a change of code the critic also gets the approach's check of errors and security: it reads the diff for errors of correctness, secrets, unchecked input, wider access and flawed dependencies, and fails the check on any of them ([profile Code](../profiles.md#code)).

## Rounds of review

A review goes in rounds: the critic reports, the author fixes, the critic reads again. A step of review has no ceiling of rounds, and the approach no number of them: the rounds go on while each finds fewer important classes of findings of the change than the one before, two findings of one class counting once (D-152). A critic who finds a problem looks for it across its whole class, not only where it showed, so that the next round does not find its neighbour.

What follows a round, by its records, is the first that holds of these branches, in this order: (1) open gate: a finding `not fixable` in a round of the task, of either step and whatever version it names, after the owner's last approval, is a question to the owner until his newer approval; (2) no round: the first round; (3) no acceptance: a round of the result with no finding on merging and no verdict of acceptance is followed by a round that gives it; (4) acceptance refused: one whose clean acceptance is refused, by a round whose acceptance holds; (5) clean: a clean round ends the step; (6) stagnation: change the design, then a full round; (7) next round: narrow, reading only the fixes, when every finding of the last round is fixed with a test, and full when one is not. The budget is no branch of a step: the task's next action, below, alone orders it, and puts a spent budget before an open gate. A verdict a narrow round does not read again is carried from the earlier round (D-95). The review of the result goes on only under an approval in force: when a later round of the statement withdraws it, the owner's approval too, `--rounds` says, as `--task` does, that work is not allowed.

Stagnation is the sign that patching does not converge: the last round has an important finding, and either an important class of it was an important finding of an earlier round of the step, or it found no fewer important classes than the round before it. Only important findings count, on both sides, so two rounds of nits are no stagnation, a class that was a nit before is no repeat, and an important finding after a round of nits only is more important classes than none, which is stagnation. The rounds compared are those after the last end of the step, a clean round of the statement, a clean round of the result whose acceptance held, judged for the version that round read and never against a later statement, or the owner's last approval; one function gives this for `--task`, `--rounds` and the check, so they name one next action; the first round with findings after it is not stagnation. On stagnation the author changes the design of the solution rather than patching it, and a full round follows; the tool cannot tell a new design from a patch, so the reviewer of that round judges it.

`not fixable` means that the finding cannot be fixed without changing what the owner decided, an item of the approved statement with its source or his answer; it goes to him, and `--task` then names that question alone. The gate holds the whole task, not only the round after it: a later clean round, even a clean acceptance or a reviewer's clean round that approves another version, does not close it, and `done.mjs` refuses while it is open. His answer is a new version of the statement with his approval, after which the rounds before it are not read and the next round takes the next free number. A finding that is an unlikely case is filed in `docs/limitations.md` with the value `limitation`, and one outside the statement in a ticket under `issues/` with `later`; the file must hold the finding's class, and a filed finding neither makes its round unclean nor counts in the comparison. In a verdict of acceptance a filed finding is an error: an item of the approved statement that is not met is not put off. The reviewer of the same round judges whether a finding belongs where it was filed (`rule.findings-filed`).

A clean round, with no finding of the change, makes the change ready to merge; a round of the review of a result is clean only with its verdict of acceptance clean too and holding, and without such a verdict the step has not ended (D-119, D-123, D-152). Whether it is merged or published is the owner's policy; the approach asks that it is followed and does not set it. The owner is asked only at his gates, on a finding `not fixable`, and when the budget with its reserve is exhausted.

## What a review costs and finds

With `reviewRounds` in the configuration, every round is a file of its own: the task, the step, the round's number and whether it was narrow, the commits, the reviewer, the tokens that are known, how many checks were listed, given and carried, and a line for each finding with its class, its weight, whether it is of the change, whether it is fixable, not fixable or filed as `limitation` or `later`, and the test that holds its fix or the file it is filed in (D-99, D-152). A line `Ceiling:` of an older record is read and decides nothing. The record is read by one grammar: its head, up to a heading line `## `, is the fields, each once, then at most one block `Findings:`, then at most one verdict of acceptance, each block only of finding lines directly under its name; any other line, a second block, a field after the blocks or a line starting with # that is not `## ` makes the record unreadable, naming the line, and so does a line `Statement-hash:` left blank, or missing from a round of the result at or after `reviewRounds.gatesFrom`, since a round that names no version would drop out of the review of its version unseen. The reviewer's notes go after the heading, and the tool does not read them. A record that cannot be read, of any task or of none, blocks every task: `--task` and `--rounds` name its correction as the one next action, and `done.mjs` refuses to record done, so that a dropped record never leaves an older approval in force. `ont-check --rounds` says what follows the last round of each task, with the task's budget by the configuration's limits (D-119), by the function `--task` uses, so that a verdict of acceptance the check refuses ends no step in either (D-123), and once a step has ten applications, one step of one task with its rounds together, what it cost and found. A step whose applications found nothing is a candidate to simplify; the owner decides, and nothing is removed by the tool.

The verdicts themselves are records of manual runs. The critic gives a table of them, and `ont-check --review <base> --record <table>` writes one record for each new verdict and none for a carried one, and refuses the table when a check is missing, unknown, given twice, carried at another stamp or over files that changed since, or is the check of errors in code, which reads every new diff (D-100).

## A task's statement and its approval

A task starts from its statement, written before work: the owner's sources for it, what to do and what not to do, its condition of done as commands and its budget; it sets no ceiling of rounds. It may live outside the repository, since it holds the owner's words; the tool reads only its lines `Done-when:`, `Budget-new-input:`, `Budget-output:` and `Budget-reserve:`, and names its version by the SHA-256 of the file (D-152).

The statement is reviewed in rounds like a change, and each round records the hash of the version it read on a line `Statement-hash:`. An approval is in force for a version when the last round of the review of the statement, by its time, is clean and read that version, or when the last of those rounds and the owner's approvals is his approval of that version (D-121, below); the approval in force at a moment is decided by the last of them before it (D-117). The same criterion lets the executor start and lets a reviewer accept the result; a later round of a new version that finds something withdraws the approval of the old one too. When the statement is edited after a clean round or the owner's approval, the next is a full round of the new version, with the next free number of the full rounds over every version, however many rounds came before; no round is counted. A next round of either kind takes the next free number of its kind, and numbers never repeat between versions.

`ont-check --task <task> --statement <file>` prints the state of the statement, of the result, of the record of done and of the budget, each a state only, and then the task's one next action, once, on a line `NEXT`. That action is the first that holds of these branches, in this order: (1) unreadable record: correct a record of rounds that cannot be read, a blank or missing `Statement-hash:` among them, or move or remove a late record; (2) done: within the current version window, the last round of the result and its acceptance are clean, and the file given is the window's version; (3) budget question: a spent budget, records of spend that overlap or a line of the budget that cannot be read is the question to the owner, ahead of an open gate; (4) open gate: a finding `not fixable` after the owner's last approval is the question to him; (5) no review: the statement needs a review; (6) under review: the next round of the statement's review; (7) no version: give the file; (8) changed: a full round of the changed statement; (9) step: with no round of the result in the window, the executor works under its version and records done, or, once that record of done is there, the first full round of the review of the result, with the next free number; otherwise the next round of the result. Three rules make every reader agree whatever version a record names, and they are stated here once (D-152). First, the open gates are read over the whole task: a finding `not fixable` in any round of either step after the owner's last approval, whatever version the round names, holds until his newer approval, and a reviewer's clean round, of the statement or of the result, never clears it. Second, a late record is refused, not read: a round of the result, with its verdict of acceptance, or a record of done that names another version than the one last approved when it ended, or none, and ends after that version's approval, cannot be read; it blocks every task in `--task`, `--rounds`, `done.mjs` and the check, and the executor moves it out of the records or removes it. Third, a round of the result at or after `reviewRounds.gatesFrom`, or any round when the key is not set, gives its `Statement-hash:`: one without it is malformed by the grammar, a fact of the record alone, so it blocks every task and no later approval hides it; an older round reads as it did. Within these rules every other reader, each branch, the acceptance, the round that ends the task and its commits, the lines of `--task`, the overspend the check compares and `done.mjs`, reads the window of the current version by one task view. The current version is the version approved now, or, while a later round withdraws its approval, the version last approved; its window starts at the first of the events at the end of the history that approve it, a clean round of the statement or the owner's approval, and the rounds of the result and records of done after that time are the window's. The rounds and records of done of an earlier window count only for the numbers of rounds and for the budget; `--task` lists them on a line `TASK <task> · not read`, and a record of done made before the version's approval was withdrawn and given again is not reused. `--rounds` prints, for every task any record names, a round or a record of spend, of done or of approval, the counts of its rounds by step and then the lines of `--task` given no file, from the same function, so its states and its `NEXT` line are `--task`'s, and `done.mjs` asks it for new work and records done only when the action is the step, so a spent budget refuses a fresh record of done after the task is done too; all three read the records by one function and give one action from the same records. One exception: before a record of done of the approved version carries its limits, `--rounds`, which reads no statement, measures the budget by the configuration's limits while `--task` measures it by the statement's, so the two may differ on the budget question alone (D-147, docs/limitations.md). Which record is legacy is decided by its time alone, never by the version it names or by the task's approvals: a round, a record of done or of approval before the configuration's `reviewRounds.gatesFrom` is legacy and reads as it did, never late, and a task all of whose records are legacy, as one recorded before D-106, skips branches 5 to 8; every record at or after the time follows the three rules, so a round of the result that names a version with no approval in force is followed by the review of the statement in `--task`, `--rounds` and `done.mjs`, never by a round of the result. The state of the result calls the last round's clean verdict of acceptance refused, with why, when it does not hold for the window's latest record of done. A finding `not fixable` written before the configuration's `reviewRounds.gatesFrom` carries its earlier meaning, not fixable within the task, and opens no gate; this repository sets it to the time of the first record of done of task round-rules, the start of the review of the first result under D-152.

## The owner's approval

When a finding of the review of a statement goes to the owner, as one `not fixable` does, he may approve a version himself. The thread that carries out his answer writes it in the directory of `taskRecords`: `Record: approval`, the task, `Statement-hash:` of the version, `By: owner`, `Source:` with his words or answer and the date, and the time in UTC. It counts beside the rounds: the last by time of the rounds of the statement and the owner's approvals decides, so his approval lets work start and a result be accepted, and a later round with findings withdraws it. A record without a source, or by anyone but the owner, cannot be read: the check fails and nothing is approved. The tool never writes one (D-121).

## Acceptance after done

When the executor is done, `done.mjs <task> --statement <file>` runs the statement's commands of done on the commit in a temporary worktree and, under an approval in force for that version and only when every command passed, writes the record of done in the directory of `taskRecords`: the task, the commit, the hash of the statement, the statement's limits and reserve as its lines `Budget-new-input:`, `Budget-output:` and `Budget-reserve:` give them, or `none`, the time the commands had run, to the second in UTC, and each command with its result (D-152, D-147).

Then a reviewer checks the result against the approved version: every item of what to do and of done when, and the owner's sources. The verdict of acceptance is written in the same round of the review of the result, beside the verdict on merging, as `Acceptance: clean` or as `Acceptance:` with a finding line for each item the result does not meet. The round is clean only when both have no finding of the change. The round names the commit it reviewed on its line `Commits:`, the last of a range. The check refuses a verdict of acceptance with no record of done, given before the record was made, after a record with a failed check, for another version of the statement, after a record of done made with no approval in force for its version or of another commit than the one the round reviewed, or when the approval was withdrawn before the acceptance; with the statement's file, `--task` also refuses it when the file is no longer that version or when the record of done ran other commands than the file's lines `Done-when:`, exactly and in their order, and says done only for an acceptance that holds (D-117, D-123). The acceptance must be of the latest record of done of the window: after a new record of done of that version for a newer commit, `--task` and `--rounds` say the task is not done until a round accepts it, and `--task` names the latest record on a line of its own (D-128). Every commit a record names is tested in the repository by one test, `git cat-file -e`, and a missing one is an error only where what the record proves rests on it: a record of done whose commit is not there cannot be read and binds no acceptance, so the task is not done; the round that would end the task, the last round of the review of its result in the window, clean on merging and in its acceptance, whose acceptance holds for the latest record of done, an entry of `releases.md` and a record of a product release whose commit is not there are errors of the check. One function names that round, so the check, `--task` and `--rounds` all refuse its acceptance for the missing commit, and none of them calls the task done (D-148). Every other round, such as one with a finding on merging or one a later round follows, and every manual run, that names a commit the clone does not have, as a clone made after a rewrite of the history may, is information, and the check passes. A branch named in `Commits:` is not held to it, since it may be deleted after the round (D-145). An acceptance by the owner that his policy asks for, as before a publication, stays his.

## The budget of a task

A project sets a task's default limits in its configuration, `budget.newInput` and `budget.output`, and the multiplier at which it stops, `budget.reserve`; a statement's own lines replace the limits and the reserve for its task, each that it gives, `Budget-reserve:` a number of 1 or more such as `1.5` (D-150). One function says which limits apply, and `--task`, `--rounds`, the check and the text of an overspend all ask it: those of the approval in force, of the version of the statement it names, read from its file where `--task` is given that version, and otherwise from the latest record of done of that version, which carries them; a record of done of an older version gives none for a newer one, and `--task` compares with the file only a record of done of the file's version; with no approval in force, the file's; else the configuration's. Before the first record of done of the version in force, `--rounds` knows only the configuration's (D-147). The reserve is read in the same order from the same places as the limits; with limits and no reserve in the statement or the configuration the reserve is 1, and the tool says so; with no limit anywhere it says nothing of a budget. The approach sets no number (D-108).

The spend is the new input and the output of every contribution to the task, one run of a model each, named by its provider and its session or task there: the rounds of its review, which give `Contribution:` with `Start:`, and the executor's own records of spend (`Record: spend`, with a start and an end). Cached tokens are not summed. Two records of one contribution over intervals that overlap, even in part, or that begin in the same second, are an error, and so is a record that begins after it ends, which counts in no sum. While two records overlap, `--task` sums none of the spend and the next step is a question to the owner, until they are corrected (D-118); the pairs are those the check finds over the records of every task, so a session recorded in two tasks stops both (D-124). The output says for how many contributions the spend is known; the stop is decided by what is known, each value on its own.

The budget is checked when the next action is chosen, not after: run `--task` before every step of the executor and every round; a round of the result clean on merging with no verdict of acceptance yet is such a point too (D-119). When the budget with its reserve is exhausted, the next step or round is a question to the owner instead, ahead of the rules of convergence, and it is the one next action `--task` names: no line of it then lets work start or go on (D-124). A clean round that ends a step stays clean. A clean round of the review of the result, with acceptance clean, ends the task even past its budget: `--task` prints the overspend, the record of the round names it on a line `Overspend:`, exactly as the tool prints it, `new input N of L, output N of L`, each number written one way, a whole number or a decimal with a point, such as `151.5` for a limit of 101 with a reserve of 1.5; `--task` and the check refuse any other line, a missing one past the limit and one within it alike, by the same limits (D-128, D-147); and the executor reports it to the owner. A clean review of the statement ends no task, so a budget spent past it blocks the start of work.

The budget is the one hard stop. On the way to it, each run of `--task` prints a line `REPORT` with the marks the spend has passed, new input and output each on its own: `half` at half the limit or more, `limit` at the limit or more, the limit before the reserve; one contribution that passes both gives both. The line stands apart from the next action, which it does not change: work goes on below the reserve, the question comes past it, and a clean round of acceptance past it still ends the task. The executor sends the owner one report with every mark not yet reported. When the spend cannot be summed, because records of one contribution overlap, or a line of the statement's budget cannot be read, the next action is the question and no line `REPORT` is printed, since no spend is measured. How a limit comes from an estimate is the owner's rule, not the approach's (D-152).

## How it fails in practice

- **The table describes an older layout of the repository.** When paths move, update the table in the same change. Include the agent instructions file in the paths that trigger the check.
- **Rules that should be checks stay rules forever.** Review the list from time to time and ask which item could be a check.
- **A correction goes into the instructions by habit.** The agent is told once more in prose, and the next agent repeats the mistake. Ask first whether the code, a check, a test or a lint can make it impossible.
- **Instructions that quietly differ from the approach.** A project's rule says less or more than the rule of the approach it replaces, and nothing records the choice. Write the departure as a process entry and cite it from the instruction.
- **Reviews that list everything.** A finding that misleads no one costs the reader's attention and teaches agents that the list is noise. Report what would mislead a reader or an agent, or would break a check, and leave style and completeness alone.
