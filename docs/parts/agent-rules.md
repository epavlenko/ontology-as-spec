# 7. Agent rules

<!-- ont: ent.agent-rules@99af23 -->

## What it is

A section in the repository's agent instructions (`AGENTS.md` or its equivalent) that tells any agent how to keep meaning current. It has two parts: a table of what else to update when something changes, and a short list of rules the check cannot enforce.

| You changed                                        | Also update                                                                                                                                        | Verify                          |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| A concept, rule, invariant or view in the ontology | run `format-ontology.mjs`; regenerate the tooltips; a revision history line; a decision entry when the reason is new                               | the check                       |
| A rule, invariant, hook or action in the ontology  | its check in the catalogue, before the code                                                                                                        | the check                       |
| The mockup                                         | the ontology first; `data-ont` on every new meaningful element and its map row                                                                     | the check, a browser smoke test |
| Code                                               | the rows and checks it implements first; an `ont:` comment naming the concepts the code implements; the implementation table and known divergences | the check, the tests            |
| A change about to be merged                        | `ont-check --review <base>`; an agent of another provider that did not write it gives each listed check a verdict with the change-review skill     | the reviewer's verdicts         |
| Your mind about an earlier decision                | a new dated entry that supersedes the old one                                                                                                      | the check                       |
| A concept becomes implemented                      | tests that implement its automatic checks, titled with the check IDs                                                                               | the check, the tests            |
| A definition row that a help page explains         | reread the sections the check lists, then `stamp-docs.mjs`; regenerate the reference pages                                                         | the check                       |

Generated files are never edited by hand; the check compares them with what the generators write.

Rules the check cannot enforce:

- A change of behavior starts in the ontology, its rows or its checks; the code and its tests are written from it after (`rule.ontology-changes-first`). The code, the mockup included, is written from the ontology: what it would do that the ontology does not say, including what an element deliberately does not do, is a gap in the ontology, so add the row or the check, or ask, before writing it (`rule.ontology-is-source`, `rule.behavior-in-ontology`, `rule.limits-in-ontology`).
- IDs are permanent. Renaming a term changes its row's text, never its ID. An ID that has to change goes under "Retired IDs" with its replacement; only the decision log keeps using it (`inv.ids-permanent`, `action.change-id`).
- Removing a concept is a decision: write the entry and retire the ID; the check then finds every reference left (`action.remove-concept`).
- The ontology describes the target. When the code disagrees, record the divergence; do not silently change either side (`rule.divergence-becomes-work`).
- Code that implements a concept names its ID next to it in a comment, `// ont: rule.renewal` (`rule.code-names-concepts`).
- What a partial implementation leaves out is a target concept, named in the note of its row. A note alone hides the work from `--gap` (`rule.partial-noted`).
- A choice the owner has not explicitly approved, such as a value you picked when asked to tune something, is recorded as tentative; the owner's approval accepts it (`rule.unconfirmed-tentative`).
- A question you can recommend an answer to is a tentative entry, not a line under open questions: your recommendation is its decision, the other options are rejected. The entry gives you no permission to act on the recommendation; your task or the owner does. When the owner answers, the entry names the answer on its `Source:` line (`rule.question-as-tentative`, `action.answer-tentative`).
- Name where a decision was made on its `Source:` line. When sources disagree, follow the owner's latest word; an answer someone gave for the owner keeps the entry tentative (`rule.source-precedence`).
- What you put off outside any slice gets an entry with a `Return when:` line, not a note that nobody will read again (`rule.deferral-returns`).
- A number is held as its role needs. A rule's value or a requirement is held by a check. A model's assumptions are held by a snapshot of its base scenario, each change of them is a short entry about its topic, and no check requires the model to reach its goal (`rule.number-by-role`, `rule.chosen-value-checked`).
- A consistency review reports what would mislead a reader or an agent, or would break a check. Style, the completeness of lists and compliance that changes nothing are not findings (`rule.findings-mislead`).
- Every change ends with a commit of its own files, never another agent's (`rule.commit-finished-work`).
- A rule here that comes from a rule of the approach or from a decision names it, by ID or entry; a rule that departs from the approach cites the process entry of the log that decided it (`rule.agent-rule-source`, `rule.departure-by-entry`).

## Why a table

Agents follow explicit procedures well and infer side effects badly. "Remember to keep docs in sync" produces nothing. "You changed the mockup, so add the map row and run this command" produces the map row. The table turns the dependency graph between artifacts into instructions, and the Verify column turns each instruction into something checkable.

The list after the table holds only the rules no check enforces; it exists because some rules have no mechanical check yet. Writing them down is the fallback. When a rule keeps being broken, it should move from the list into the check. Encoding a lesson in structure beats repeating it in prose.

The same order applies to every correction of an agent (`rule.strongest-step`). A mistake an agent made once it will make again, so the correction is held at the strongest step that can hold it. First the structure of the code, so the mistake cannot be written: a type, a boundary in the import graph, a single way to do a thing. Then a check of the tool, a test or a lint, which fail the build. Then a rule in the agent instructions, which an agent may not read. Last, what a reviewer remembers, which does not scale with the number of changes. A rule in the instructions is the fallback for what nothing else can hold, and the list after the table is where it goes. The order follows Lauren Tan's account of how a team of agents keeps a codebase trustworthy at hundreds of changes a day ([talk, 2026-09-21](https://x.com/poteto/status/2102050467505430555)).

## Reference

The rules for the section itself are in the reference: [Agent rules](../reference.md#agent-rules). Keep it short, because it is read at the start of every session and long sections are skimmed. Let every row name a path or a command. Let every task start by naming the IDs it touches: if an agent cannot name them, the task is not about meaning, or the ontology is incomplete. The tool enforces none of this directly; it enforces the consequences, because a skipped row usually fails the check. The same restraint applies to reviews: a consistency review reports what would mislead someone or break a check, not every imperfection it can find. And every change ends with a commit, since the guard protects only accepted entries that are in a commit, and a commit keeps each step easy to undo. The commit holds only the change's own files, since other agents may work in the same checkout. Who approves a commit or a push, and when to push, the approach leaves to the user; a project that does not let agents commit writes that as a process entry, as the next section shows.

## Where a rule comes from

A project's ontology is about its product. How its agents work is described by the approach's own ontology: the rules of this part and of the decision log are concepts of the approach, with IDs like any product's. So a process rule in a project's agent instructions, one that says how agents work rather than what the product is, names where it comes from: the rule of the approach it follows, by ID, or the entry of the project's log that decided it.

```markdown
- Every change ends with a commit of its own files (`rule.commit-finished-work`).
```

In the instructions, `D-nn` always means an entry of the project's own log; a rule of the approach is cited by its ID, never by the approach's entry numbers. The files stay prose, and commands and matters of style name nothing.

A project may depart from a rule of the approach, more strictly or more loosely, but only by an entry of its log that says so. A `Layer: process` line marks the entry as one about how agents work, and an `Extends:` or `Overrides:` line names the rule; the instruction that departs cites the entry. In one project that uses the approach, the agent instructions said by default not to commit and not to open a pull request. That narrowed `rule.commit-finished-work`, and nothing said so: an agent that knew the approach could not tell whether the project meant it, or why. Written as a departure, it is an entry:

```markdown
### D-63 · Agents leave commits and pull requests to the owner

- Date: 2026-10-27 · Status: accepted
- Source: the owner's message of 2026-10-27
- Layer: process
- Overrides: `rule.commit-finished-work`
- Decision: agents do not commit or open a pull request unless the task asks; a finished task ends with a list of the accepted entries that are not protected yet.
- Why: …
```

and an instruction that cites it:

```markdown
- Do not commit or open a pull request unless the task asks; say which accepted entries are not protected yet (`rule.commit-finished-work`, overridden by D-63).
```

The configuration lists the instruction files under `agentInstructions`. The check fails on a concept ID they mention that neither the project's ontology nor the approach defines, or that is retired, and on an entry they cite that the log does not have or that a later entry supersedes. It also fails on an entry with an `Extends:` or `Overrides:` line that lacks `Layer: process`, or on such a line that is empty or names something the approach does not define; while the entry is in force, a rule the approach has retired fails too, and a superseded entry, which is history, may still name one. A retired ID of the project stays retired where the approach has the same ID, and file names such as `action.yml` are not read as IDs. The approach's IDs travel with the tool, in `tools/ont-check/approach.json`, which the approach generates from its own ontology; a project copies it with the other files of the tool.

What the tool cannot tell is which lines are process rules, and whether a rule written in prose is stricter or looser than the approach. A reviewer reads the instructions for that: a process rule that names no source is a finding, and so is a departure without an entry.

## An independent critic

Before a change is merged, an agent of another provider that did not write it reviews it. Two agents of the same provider tend to share blind spots, and a reviewer handed the author's conclusions tends to confirm them, so the critic gets the diff and the IDs it touches, not the author's summary.

`ont-check --review <base>` gives the critic its checks, in two lists, the checks of review, which it gives a verdict reading the change, and the checks of run, which it carries out on the working product or has carried out (D-165): the project's checks whose concepts the change touches, through a changed definition row, a changed check, a changed file that names the concept in `ont:` or is in its implementation row, a changed doc section anchored to it or a changed ticket that lists it, or a changed file under a directory the configuration names under `reviewPaths`, which data files without `ont:` names need, and a check of run also when a changed section of its run guide names it; and the approach's checks for the kinds of artifact the change touches, such as the Decision section when the decision log changed, or the checks of run of the mockup when the mockup changed. The approach's checks of review and of run travel with the tool, each check of run with its section of the [run guide](../run-guide.md), which `--review` prints with a link at the commit the copy came from; when the copy of the tool is updated, the approach's checks of run whose guide changed are listed too. Until a later step of the approach, a check of run gets its verdict in the critic's table like any other: the critic carries it out by its guide, or gives not run with the reason. The critic follows the [change-review skill](../../skills/change-review/SKILL.md) and gives each check a verdict: pass, fail, not run when the check applies but could not be carried out, such as one that needs the running product, or not applicable, each with its evidence or reason. A check that could not be run is never written off as not applicable. A fail, or a finding of the change that remains, stops the merge; a not run with its reason does not stop it on its own (D-165). A verdict counts while the check's stamp is the one it was given at and the later commits change none of the files the critic read for it; a check whose case, concepts or files changed gets a new verdict, the check of errors and security reads every new diff, and the others stand (D-165). In the range of fixes after the narrow round that follows a confirmed condition, what counts is what `rule.fixes-held-by-tests` says instead, [below](#after-the-narrow-round): a fail or a finding of the usual path of the one issue of verdicts on the diff of the fixes stops no merge once fixed with a test, the verdicts of that issue count though the files they read change by those fixes, and the check of errors and security reads the diff of the fixes once, in that issue (D-182, D-165). The approach's checks of a judge and of the screens come only when the change touches a judge, a judged check, a view or a screen, or a file the configuration does not describe (D-98). While the brief of a round after stagnation is kept in the working copy, carrying `Cause:`, the critic gets the check of the analysis of the cause, `check.review-round.redesign-after-stagnation`, whatever the change touches, and its verdict is recorded with the others before `round.mjs record` writes the round and removes the brief (D-184). For a change of code the critic also gets the approach's check of errors and security: it reads the diff for errors of correctness, secrets, unchecked input, wider access and flawed dependencies, and fails the check on any of them ([profile Code](../profiles.md#code)).

## Rounds of review

A review goes in rounds: the critic reports, the author fixes, the critic reads again. A step of review has no ceiling of rounds, and the approach no number of them: the rounds go on while each finds fewer important classes of findings of the change than the one before, two findings of one class counting once (D-152). A critic who finds a problem looks for it across its whole class, not only where it showed, so that the next round does not find its neighbour.

What follows a round: the next action of a round is the line `NEXT <task>:` of `--task` and `--rounds`, given by the ordered branches of [`derived.next-round`](../../ontology.md) and the one end of a step defined there; this guide does not restate them (D-182). The budget is no branch of a step: the task's next action, below, alone orders it. A verdict a narrow round does not read again is carried from the earlier round (D-165). The review of the result goes on only under an approval in force: when a later round of the statement withdraws it, the owner's approval too, `--rounds` says, as `--task` does, that work is not allowed.

Before any fix, the executor triages every finding of the round, important or nit: usual path, when it breaks the goal's condition on the usual path, or a rare history. A finding is usual path only when the executor names the concrete step of usual work it breaks; otherwise it is a rare history; he writes the step named in the notes of the round's record next to the finding, and the tool does not read it ("1028 a"). The reviewer marks each finding `usual` or `rare` as advice; the executor decides, either way, and writes the weight and the filing on the finding's line of the record he commits, which is what the tool reads. A rare history is filed, `limitation` or `later`, in the commit of the round's record, with no new record of done and no new round; filed findings count neither in the comparison nor in stagnation, so stagnation and the analysis of its cause follow from the usual path alone (`rule.executor-triage`, D-182). A finding of acceptance is never filed, and a nit is fixed or filed like any other.

The reviewer of a result writes `Condition: holds` or `Condition: not yet` in every reply: whether the goal's condition by the approved statement is met. The executor carries `holds` into the round's record (`field.review-round.condition`). The reviewer of a round after another reads the fixes, the executor's marks, kept fixable ones too, and the filings ("1020 b").

Stagnation is the sign that patching does not converge: the last round has an important finding, and either an important class of it was an important finding of an earlier round of the step, or it found no fewer important classes than the round before it. Only important findings count, on both sides, so two rounds of nits are no stagnation, a class that was a nit before is no repeat, and an important finding after a round of nits only is more important classes than none, which is stagnation. The rounds compared are those after the last end of the step, a clean round of the statement, a clean round of the result whose acceptance held, judged for the version that round read and never against a later statement, or the owner's last approval; one function gives this for `--task`, `--rounds` and the check, so they name one next action; the first round with findings after it is not stagnation. On stagnation the author first writes a short analysis of the cause: for a repeated class, why the earlier fix did not hold and the one cause behind it; for no fewer important classes and no repeat, why the round found no fewer. By it, the design changes where the cause lies in it, the error is fixed otherwise, and a rare case is filed (`rule.findings-filed`, D-182). The author gives the analysis to `round.mjs brief` with `--cause <file>`, below, and then the round `derived.next-round` names follows, full, or after a stagnating round that confirmed the condition the one narrow round; after the one round that follows a confirmed condition no round follows ([below](#after-the-narrow-round)). The tool sees that an analysis was given, by its hash, not whether it names the cause, so the reviewer of the next round judges whether it does and whether what was chosen follows from it.

`not fixable` means that the finding cannot be fixed without changing what the owner decided, an item of the approved statement with its source or his answer; it goes to him, and `--task` then names that question alone. The gate holds the whole task, not only the round after it: a later clean round, even a clean acceptance or a reviewer's clean round that approves another version, does not close it, and `done.mjs` refuses while it is open. His answer to the gate, `approve.mjs --kind gate --round <file of the round>`, closes the gate of that round alone, and the other gates stay open; it approves no version, so the version keeps its approval or its lack of one: on the step of the statement the next is a full round of the statement corrected by his answer, and on the step of the result the work and the next round under the approval in force ([below](#the-owners-approval), D-185). Where he approves a version instead, his approval closes every gate before it, the rounds before it are not read and the next round takes the next free number. A rare history is filed in `docs/limitations.md` with the value `limitation` only when it is what the approach does not do by choice, and a fault of the tool or a finding outside the statement in a ticket under `issues/` with `later` ("1021 b"); the file must hold the finding's class, and a filed finding neither makes its round unclean nor counts in the comparison. In a verdict of acceptance a filed finding is an error: an item of the approved statement that is not met is not put off. Whether a finding belongs where it was filed is the executor's decision; the tool does not see it, and the reviewer of the next round, if there is one, may name a wrong filing as a finding (`rule.findings-filed`).

The end of the step of the review of the result makes the change ready to merge; without a verdict of acceptance that holds the step has not ended, and after the narrow round that follows a confirmed condition it ends either with that narrow round, when it has no finding of the change and its verdict of acceptance holds, and the change is merged at once, or, after a narrow round with findings, with the record of done after the fixes that ends the range of fixes (D-182). Whether it is merged or published is the owner's policy; the approach asks that it is followed and does not set it. The owner is asked only at his gates, which `derived.next-round` names, and when the budget with its reserve is exhausted.

## After the narrow round

Once the reviewer of the result has confirmed the goal's condition and the narrow round that follows the confirmation has not ended the step, no round of review and no question to the owner follow it; the owner is asked only on a finding `not fixable` and on a spent budget ("1020 b", D-182). `--task` names one next action. A clean narrow round, its verdict of acceptance holding and no finding of the change in it, ends the step: the change is merged at once, with no fixes, no issue of verdicts and no new record of done. When the narrow round has no verdict of acceptance, or one the tool refuses, as one of another commit, its reviewer gives the verdict again on the same result; it is recorded after the narrow round with the next narrow number and read as the narrow round's, and it is no new round. Otherwise the executor fixes each finding of the usual path of the narrow round, a finding of its acceptance too, and closes each by a test; a finding of the usual path is never filed, and a rare one is filed as the triage above says. Then a reviewer of another provider gives one issue of verdicts on the diff of the fixes, `ont-check --review <the narrow round's commit> --record <table>`, which `--review` names as that issue and which is no round: the check of errors in code is given once there, its verdicts count for the merge though the files they read changed after, and a stamp that a fix changed does not make them stop being current. The findings of that issue, its fails and those its reviewer reports, are fixed with a test with no new issue when they are of the usual path, and filed when they are rare. Then `done.mjs` records done on the last commit of the fixes, and the change is merged within the owner's gates; a clean narrow round is merged as it is (D-165).

The commits between the narrow round's commit and that record of done are the range of fixes (`rule.fixes-held-by-tests`). One function of the tool gives it from the records that exist, the narrow round's `Commits:` and the record of done's `Commit:`, and ends it at the head of the working copy, for `done.mjs` the commit it records done on, while there is no such record of done; `--task`, `--rounds`, `done.mjs`, `--review`, the check's current records and `merge-gate.mjs records-only` ask it alike. Before the merge, records-only compares the head, outside `reviews/`, after a clean narrow round, which no fixes and no record of done follow, with the commit that round reviewed, the one the reviewer checked, merged with main, and after a narrow round with findings with the commit of the record of done that ends the range, merged with main too; never with the head; a commit after the record of done is outside the range, and a change in it is refused as any change no reviewer read. A record of a gate change still names the last commit of the pull request outside `reviews/`. Where the configuration at the base sets `mergeGate.verdicts`, the guard sees both: that the issue was given at the commit the record of fixes names, and that each finding has a test the record of done shows passed ([below](#verdicts-at-the-merge)).

## Verdicts at the merge

Where the configuration at the base of a pull request sets `mergeGate.verdicts`, the guard holds the merge of a change of a task by its verdicts, from the records alone (D-186). The list of the change is what `--review` of the root gives on the diff from the merge base to the checked commit, the commit the merge by the state of the task compares the head with; the base's code computes it from Git's objects in a working tree of its own, and runs nothing of the pull request. Each check of that list needs its verdict of the change: the latest record of it, of any verdict, on the checked commit, or a fresh record of a run outside a review. A record of an earlier result at the same stamp does not count, since the stamp does not cover the files the reviewer read; an earlier verdict reaches the checked commit only by a carry `--record` checked, which writes a record of its own. A pass holds; a `not run` or `not applicable` holds with its reason; a fail holds when each class of its findings, which the reviewer names in square brackets at the start of its evidence, is filed by a round of the result or held by a test in the record of fixes. Otherwise the guard refuses, `VERDICT_MISSING`, `VERDICT_FAILED`, `VERDICT_UNREASONED`, or `VERDICT_NOT_OF_CHANGE` for the check of errors in code given on another commit, a commit of records alone among them. `--record` writes on the last commit outside the records.

After a narrow round with findings, the one issue of verdicts is named by the record of fixes, `round.mjs fixes --issue <commit>`, with the classes of the issue's table of findings. Each check of the final list is held by the issue when the issue lists it, else by the record of the result the narrow round checked, else by the range of fixes, with no verdict, since the final diff chose it only because of the fixes; partial lists are never added up. Each finding of the issue and of the usual path of the narrow round is decided by a test that `done.mjs` ran alone on the commit of done and wrote under `Fix-tests:`, or by a filing; otherwise `ISSUE_MISSING` or `FIX_UNTESTED`.

One function gives the end of a step, for `--task`, `done.mjs`, the guard, the brief and the windows of rounds: the later of the round that ended it and the record of done that ended the range of fixes. A record of done after that end on another commit is a new result, and one narrow round on it follows. A round after a round with findings in the open window needs the verdicts of the record of a round, `check.review-round.filed-right`, `check.review-round.whole-class` and, after stagnation, `check.review-round.redesign-after-stagnation`; `round.mjs record` refuses it without them, and at the merge a fail among them not decided in the window holds the merge. A failed analysis of the cause is decided only by a later pass on the corrected analysis.

## What a review costs and finds

With `reviewRounds` in the configuration, every round is a file of its own: the task, the step, the round's number and whether it was narrow, the commits, the reviewer, the tokens that are known, how many checks were listed, given and carried, and a line for each finding with its class, its weight, whether it is of the change, whether it is fixable, not fixable or filed as `limitation` or `later`, and the test that holds its fix or the file it is filed in, and on a review of the result `Condition: holds` when the reviewer confirmed the goal's condition (D-99, D-152, D-182), and on a round briefed after stagnation `Cause:`, the SHA-256 of the analysis of the cause it was briefed with, a round without it reading as before (D-183). A line `Ceiling:` of an older record is read and decides nothing. The record is read by one grammar: its head, up to a heading line `## `, is the fields, each once, then at most one block `Findings:`, then at most one verdict of acceptance, each block only of finding lines directly under its name; any other line, a second block, a field after the blocks or a line starting with # that is not `## ` makes the record unreadable, naming the line, and so does a line `Statement-hash:` left blank, or missing from a round of either step at or after `reviewRounds.gatesFrom`, since a round that names no version would drop out of the review of its version unseen. The reviewer's notes go after the heading, and the tool does not read them. A record that cannot be read, of any task or of none, blocks every task: `--task` and `--rounds` name its correction as the one next action, and `done.mjs` refuses to record done, so that a dropped record never leaves an older approval in force. `ont-check --rounds` says what follows the last round of each task, with the task's budget by the limits of the version approved now, read from the records of that version since `--rounds` takes no statement file: its kept brief, its latest record of done, its latest record of the owner's approval that carries the limits, or else its latest snapshot of spend (D-176), and by the configuration's limits only when no record gives them (D-182, D-152), by the function `--task` uses, so that a verdict of acceptance the check refuses ends no step in either (D-182), and once a step has ten applications, one step of one task with its rounds together, what it cost and found. A step whose applications found nothing is a candidate to simplify; the owner decides, and nothing is removed by the tool.

The verdicts themselves are verdict records. The critic gives a table of them, and `ont-check --review <base> --record <table>` writes one record for each new verdict, each pass or fail with its `Performer:`, `agent` unless the row names another, and none for a carried one (D-165), and refuses the table when a check is missing, unknown, given twice, carried at another stamp or over files that changed since, or is the check of errors in code, which reads every new diff (D-100).

## A task's statement and its approval

A task starts from its statement, written before work: the owner's sources for it, what to do and what not to do, its condition of done as commands and its budget; it sets no ceiling of rounds. It may live outside the repository, since it holds the owner's words; the tool reads only its lines `Done-when:`, `Budget-new-input:`, `Budget-output:`, `Budget-reserve:`, `Goal:`, the goal whose budget and reserve the task also counts against ([below](#the-budget-of-a-task), D-179), and `Gate-paths:`, the gate paths the task may change, which the brief and the round of the review of the statement and the owner's approval carry, so that the guard, which reads no statement, finds them in the approval in force (D-185); the writer of gate-change records also reads the numbers of the items of What to do, to check the item a record names (D-170); it names its version by the SHA-256 of the file (D-152).

The statement is reviewed in rounds like a change, and each round records the hash of the version it read on a line `Statement-hash:`. An approval is in force for a version when the last round of the review of the statement, by its time, is clean and read that version, or when the last of those rounds and the owner's approvals is his approval of that version (D-121, below); the approval in force at a moment is decided by the last of them before it (D-182). The same criterion lets the executor start and lets a reviewer accept the result; a later round of a new version that finds something withdraws the approval of the old one too. When the statement is edited after a clean round or the owner's approval, the next is a full round of the new version, with the next free number of the full rounds over every version, however many rounds came before; no round is counted. A next round of either kind takes the next free number of its kind, and numbers never repeat between versions.

`ont-check --task <task> --statement <file>` prints the state of the statement, of the result, of the record of done and of the budget, each a state only, and then the task's one next action, once, on a line `NEXT`. That action is the first that holds of these branches, in this order: (1) unreadable record: correct a record of rounds that cannot be read, a blank or missing `Statement-hash:` among them, or move or remove a late record; (2) rules drift: before each step `--task` compares the rules of main on GitHub with the rule file, every field, with the executor's `gh`, and a difference is the question to the owner, who alone changes them; where they cannot be compared, a line `RULES` says why and the action stays (D-185); (3) done: within the current version window, the last round of the result ends its step, as the end of a step above says, or the record of done after the narrow round ends the range of fixes ([below](#after-the-narrow-round)), and the file given is the window's version; the change is merged, and past the reserve of the goal or of the task the overspend is reported to the owner with it, by the same spend the budget question reads, from the logs or, with none, the snapshot the round that ends the task names (D-169); (4) budget question: a spent budget, records of spend that overlap, a line of the budget that cannot be read or an approved file with no command of done (`Done-when:`) is the question to the owner, ahead of an open gate; (5) open gate: a finding `not fixable` after the owner's last approval is the question to him; (6) no review: the statement needs a review; (7) under review: the next round of the statement's review; (8) no version: give the file; (9) changed: a full round of the changed statement; (10) step: with no round of the result in the window, the executor works under its version and records done, or, once that record of done is there, the first full round of the review of the result, with the next free number; otherwise the next round of the result. Three rules make every reader agree whatever version a record names, and they are stated here once (D-152). First, the open gates are read over the whole task: a finding `not fixable` in any round of either step after the owner's last approval, whatever version the round names, holds until his answer to the gate of that round or his newer approval of a version (D-185), and a reviewer's clean round, of the statement or of the result, never clears it. Second, a late record is refused, not read: a round of the result, with its verdict of acceptance, or a record of done that names another version than the one last approved when it ended, or none, and ends after that version's approval, cannot be read; it blocks every task in `--task`, `--rounds`, `done.mjs` and the check, and the executor moves it out of the records or removes it. Third, a round of either step at or after `reviewRounds.gatesFrom`, or any round when the key is not set, gives its `Statement-hash:`: one without it is malformed by the grammar, a fact of the record alone, so it blocks every task and no later approval hides it; an older round reads as it did. Within these rules every other reader, each branch, the acceptance, the round that ends the task and its commits, the lines of `--task`, the overspend the check compares and `done.mjs`, reads the window of the current version by one task view. The current version is the version approved now, or, while a later round withdraws its approval, the version last approved; its window starts at the first of the events at the end of the history that approve it, a clean round of the statement or the owner's approval, and the rounds of the result and records of done after that time are the window's. The rounds and records of done of an earlier window count only for the numbers of rounds and for the budget; `--task` lists them on a line `TASK <task> · not read`, and a record of done made before the version's approval was withdrawn and given again is not reused. `--rounds` prints, for every task any record names, a round or a record of spend, of done or of approval, the counts of its rounds by step and then the lines of `--task` given no file, from the same function, so its states and its `NEXT` line are `--task`'s, but that where the configuration counts spend from the logs it names no action by the budget, neither the question to the owner nor an overspend to report, which only `--task` names ([below](#spend-from-the-session-logs)), and `done.mjs` asks it for new work and records done only on an action of kind work: each action carries its kind, set where it is decided, work, review, question, correct or done, and a question of the step, as a legacy finding `not fixable` in the last round of the result, is of kind question, so a spent budget refuses a fresh record of done after the task is done too; all three read the records by one function and give one action from the same records. One exception: `--rounds`, which reads no statement, measures the budget by the limits of the version in force as a record of that version holds them, its kept brief, its record of done or its snapshot of spend, and by the configuration's only when none does, while `--task` measures it by the statement's, so for a version approved before any record of it holds its limits the two may differ on the budget question alone (D-174, [ticket 8](../../issues/0008-budget-stops-without-measured-spend.md)). Two questions are kept apart. How a record is read is decided by its time alone: a round, a record of done or of approval before the configuration's `reviewRounds.gatesFrom` is legacy and reads as it did, never late, its `not fixable` opening no gate; every record at or after the time follows the three rules. Whether a task follows the approval of versions above, branches 6 to 9, is decided by its records, never by the time: once any record of it names a version, a round with `Statement-hash:`, a record of done or of the owner's approval, it does, so a task versioned before the time still needs its file and an approval in force, and a round of the result that names a version with no approval in force is followed by the review of the statement in `--task`, `--rounds` and `done.mjs`, never by a round of the result; only a task none of whose records names a version, as one recorded before D-106, skips branches 6 to 9, and by the third rule all its records are before the time. `done.mjs` asks for that action before any refusal of its own and refuses with its text, so with no approval in force a spent budget or an open gate is its refusal too. The state of the result calls the last round's clean verdict of acceptance refused, with why, when it does not hold for the window's latest record of done. A finding `not fixable` written before the configuration's `reviewRounds.gatesFrom` carries its earlier meaning, not fixable within the task, and opens no gate; this repository sets it to the time of the first record of done of task round-rules, the start of the review of the first result under D-152.

## The owner's approval

When a finding of the review of a statement goes to the owner, as one `not fixable` does, he may approve a version himself, or answer the gate of a round. The executor writes his answer with `approve.mjs <task> --statement <file> --question <N> --kind approval` or `--kind gate --round <file of the round>`, `--english <file>` giving the English translation of his words: it reads the answer from the registry of questions by the command the environment names in `ONT_REGISTRY_CMD`, and writes nothing when the registry has no answer of his, when the question does not name the task and the version, or the round, or when the option he chose does not approve or does not answer the gate (D-170). The record is in the directory of `taskRecords`: `Record: approval`, its kind, the task, `Statement-hash:` of the version, `By: owner`, the question, `Source:` with the question, the date, the option and his words translated, and the time in UTC, sealed. It counts beside the rounds: the last by time of the rounds of the statement and the owner's approvals decides, so his approval lets work start and a result be accepted, and a later round with findings withdraws it. A record without a source, or by anyone but the owner, cannot be read: the check fails and nothing is approved. His answer to a gate closes the gate of the round it names and no other, and approves no version: the approval in force after it is the one before it; on the step of the statement the next is a full round of the statement corrected by his answer, and on the step of the result the work and the next round under the approval in force (D-185). An approval carries the statement's `Gate-paths:`.

## Acceptance after done

When the executor is done, `done.mjs <task> --statement <file>` runs the statement's commands of done on the commit in a temporary worktree and, under an approval in force for that version and only when every command passed, writes the record of done in the directory of `taskRecords`: the task, the commit, the hash of the statement, the statement's limits and reserve as its lines `Budget-new-input:`, `Budget-output:` and `Budget-reserve:` give them, or `none`, the time the commands had run, to the second in UTC, and each command with its result (D-152, D-147). What the statement asks the record of done to name besides the commands, such as each row of the catalogue the task changed, goes in a file given with `--evidence FILE`, whose lines go under a line `Evidence:` after the checks, where the reviewer of acceptance reads them; where `records.latinOnly` is set they hold English text and paths of the repository only, or nothing is written (D-166).

Where the configuration at the base of a pull request sets `mergeGate.taskState`, the guard of the merge reads the task's next action at the head from the same records, so a result with no record of done, or whose acceptance does not hold, is not merged ([lifecycle](../lifecycle.md#the-state-of-the-task), D-185). Then a reviewer checks the result against the approved version: every item of what to do and of done when, and the owner's sources. The verdict of acceptance is written in the same round of the review of the result, beside the verdict on merging, as `Acceptance: clean` or as `Acceptance:` with a finding line for each item the result does not meet. The round is clean only when both have no finding of the change. The round names the commit it reviewed on its line `Commits:`, the last of a range. The check refuses a verdict of acceptance with no record of done, given before the record was made, after a record with a failed check, for another version of the statement, after a record of done made with no approval in force for its version or of another commit than the one the round reviewed, or when the approval was withdrawn before the acceptance; with the statement's file, `--task` also refuses it when the file is no longer that version or when the record of done ran other commands than the file's lines `Done-when:`, exactly and in their order, and says done only for an acceptance that holds (D-182). The acceptance must be of the latest record of done of the window: after a new record of done of that version for a newer commit, `--task` and `--rounds` say the task is not done until a round accepts it, and `--task` names the latest record on a line of its own (D-182). Every commit a record names is tested in the repository by one test, `git cat-file -e`, and a missing one is an error only where what the record proves rests on it: a record of done whose commit is not there cannot be read and binds no acceptance, so the task is not done; the round that would end the task, the last round of the review of its result in the window, clean on merging and in its acceptance, whose acceptance holds for the latest record of done, an entry of `releases.md` and a record of a product release whose commit is not there are errors of the check. One function names that round, so the check, `--task` and `--rounds` all refuse its acceptance for the missing commit, and none of them calls the task done (D-182). Every other round, such as one with a finding on merging or one a later round follows, and every manual run, that names a commit the clone does not have, as a clone made after a rewrite of the history may, is information, and the check passes. A branch named in `Commits:` is not held to it, since it may be deleted after the round (D-145). After the narrow round that follows a confirmed condition, the acceptance of the result is that round's verdict of acceptance, held by these rules as the records were when it was given, together with the record of done after the fixes, with no new acceptance ([below](#after-the-narrow-round)). An acceptance by the owner that his policy asks for, as before a publication, stays his.

## Records written by the tool

Every record of the process is written by a writer of the tool, never by hand, and carries its seal on its first line, `Seal: v1 <sha256>`, the hash of the rest of the file after the prefix of its format (D-167). Where the configuration at the base of a pull request sets `records.sealsFrom`, the guard `ont-gate-guard` refuses a record the pull request adds after the merge that brought the key without a seal that is its text's, `SEAL_MISSING` or `SEAL_WRONG`, and always refuses a record of the base, or one an earlier commit of the pull request added, that is changed or removed, `RECORD_CHANGED` or `RECORD_REMOVED`; a correction is a new record. The full check and pre-commit say the same as information, reading the start of seals as the guard does, at the base a pull request of the branch has, the tip of main, never at the branch's own configuration, so that the pull request that brings the key is told of no refusal (D-181). A seal does not stop a deliberate forgery ([limitations](../limitations.md)).

- **A round**, in two steps (D-183). Before it, `round.mjs brief <task> --step statement|result --statement <file>` gives the brief's lines, kept once in the Git directory of the working copy, only when the task's next action is that round: for the statement, once the file is corrected since the last round with findings; for the result, once a record of done newer than the last round is on a commit whose tree differs, the records of the rounds of the step and of done aside, or for the verdict of acceptance alone on the same result. When the next action names stagnation, the brief needs `--cause <file>`, the analysis of the cause, and is refused without it; it prints the analysis after the lines and carries its SHA-256 on `Cause:`, which the round's record copies, while `--cause` is refused where no stagnation is named (D-182). The lines open the reviewer's brief, with the analysis after them, and the reviewer's reply begins with them word for word. After it, `round.mjs record <task> --from <reply> --triage <file>`, run in the same working copy with the same environment, writes the round from the reply the review skill asks for and the executor's triage, taking the task's limits as those of the brief's version, whose lines `Budget-new-input:`, `Budget-output:` and `Budget-reserve:` the brief wrote from the statement, whatever version is approved in force, and the scope of the budget as the goal the line `Goal:` names, of the statement given or with none of the task's records of the brief's version, the brief among them (D-179), so that with no statement given a task of a goal keeps its goal, and the round of a statement, a first one or a revision reviewed while an earlier version is approved, writes its snapshot under its own version with that version's limits and reserve (D-172, D-176); one line for each finding, `<class> · usual path: <the step it breaks>`, `· not fixable`, `· limitation` or `· later: issues/NNNN.md`; it refuses a reply that differs from the brief, a finding with no triage and a finding of acceptance filed.
- **The tests of the fixes**: `round.mjs fixes <task> --round <file> --from <file>` writes, for each class of a fixable finding of the round, the test that holds it, `class · file · name`; the round's record stays as it was, and the next round reads the test from the record of fixes.
- **The verdicts**: `--review --record` (`Origin: review`); a run of a check of run outside a review, in two steps, `--run-start <check>` before it and `--run-record <check> --verdict … --performer … --by … --evidence …` after it, on one committed state (`Origin: run`), which `--review` carries while nothing outside the records changed since (D-171).
- **Done**: `done.mjs`. **The owner's approval and his answer to a gate**: `approve.mjs`, above, which copies the statement's `Budget-new-input:`, `Budget-output:` and `Budget-reserve:` onto the record, as `done.mjs` does, so that the record is one of the version it approves for its limits (D-176), and on an approval its `Gate-paths:` (D-185). **The owner's permission to publish**: `approve.mjs --kind publish --scope <goal or task> --question <N> --english <file>`, from his answer whose option has the value `publish`, with no statement ([lifecycle](../lifecycle.md#the-state-of-the-task), D-185).
- **The gate records** (D-170): `gate-record.mjs change <task> --statement <file> --clause <item> --paths <paths> --base <main>` on the last commit outside `reviews/`, one record for each item of What to do that allows a change of gate paths, and `--refresh` after any later commit outside `reviews/`; `gate-record.mjs proof <task> --gate <gate> --check <check> --pr <n> --kind refusal|pass --repo <owner>/<repo> --response <file>` after the merge, from the pull request and its runs, with the base its checks ran on, never the base read back after the merge: for a pass, the first parent of its merge commit, and the writer refuses a pass whose first parent is not an ancestor of its head; for a refusal, the base read before main moves on, given with `--base <commit>` (D-180).

## The budget of a task

A project sets a task's default limits in its configuration, `budget.newInput` and `budget.output`, and the multiplier at which it stops, `budget.reserve`; a statement's own lines replace the limits and the reserve for its task, each that it gives, `Budget-reserve:` a number of 1 or more such as `1.5` (D-150). Limits belong to a version of the statement. One function gives the limits and the reserve of one version, and every reader asks it with the version that applies to what it reads (D-176): the version's own lines, from its file where the file given is that version, or else as a record of that version copies them, the task's kept brief that names it, its latest record of done of it or its latest record of the owner's approval of it, or else the latest snapshot of spend of the task that names it, which holds what its writer compared with; a record of another version gives none; each limit and the reserve the configuration's where none holds it or the version gives none. `round.mjs record`, and so the snapshot of a round, asks for its brief's version, the text of an overspend for the version its round names, and `--task`, `round.mjs brief`, `--rounds`, the check and `done.mjs` for the version in force, so that the brief writes the round `--task` names and refuses for the budget only the round for which `--task` names the question (D-176): that of the approval in force, or with none the file given, or else the version of the task's kept brief, or else the version its latest round names. `--task` compares with the file only a record of done of the file's version (D-147). A version the owner approves through `approve.mjs` has its limits from that record before any other; one approved by a record written before the record carried limits gives the configuration's until its first brief, record of done or snapshot. The reserve is read in the same order from the same places as the limits; with limits and no reserve in the statement or the configuration the reserve is 1, and the tool says so; with no limit anywhere it says nothing of a budget. The approach sets no number (D-108).

The spend is the new input and the output of every contribution to the task, one run of a model each, named by its provider and its session or task there: the rounds of its review, which give `Contribution:` with `Start:`, and the executor's own records of spend (`Record: spend`, with a start and an end). Cached tokens are not summed. Two records of one contribution over intervals that overlap, even in part, or that begin in the same second, are an error, and so is a record that begins after it ends, which counts in no sum. While two records overlap, `--task` sums none of the spend and the next step is a question to the owner, until they are corrected (D-118); the pairs are those the check finds over the records of every task, so a session recorded in two tasks stops both (D-124). The output says for how many contributions the spend is known; the stop is decided by what is known, each value on its own.

The budget is checked when the next action is chosen, not after: run `--task` before every step of the executor and every round; a round of the result clean on merging with no verdict of acceptance yet is such a point too (D-182). When the budget with its reserve is exhausted, the next step or round is a question to the owner instead, ahead of the rules of convergence, and it is the one next action `--task` names: no line of it then lets work start or go on (D-124). A clean round that ends a step stays clean. A clean round of the review of the result, with acceptance clean, ends the task even past its budget: `--task` prints the overspend, the record of the round names it on a line `Overspend:`, exactly as the tool prints it, `new input N of L, output N of L`, each number written one way, a whole number or a decimal with a point, such as `151.5` for a limit of 101 with a reserve of 1.5; `--task` and the check refuse any other line, a missing one past the limit and one within it alike, by the same limits (D-182, D-147); and the executor reports it to the owner. A clean review of the statement ends no task, so a budget spent past it blocks the start of work.

The budget is the one hard stop. On the way to it, each run of `--task` prints a line `REPORT` with the marks the spend has passed, new input and output each on its own: `half` at half the limit or more, `limit` at the limit or more, the limit before the reserve; one contribution that passes both gives both. The line stands apart from the next action, which it does not change: work goes on below the reserve, the question comes past it, and a clean round of acceptance past it still ends the task. The executor sends the owner one report with every mark not yet reported. When the spend cannot be summed, because records of one contribution overlap, or a line of the statement's budget cannot be read, the next action is the question and no line `REPORT` is printed, since no spend is measured. How a limit comes from an estimate is the owner's rule, not the approach's (D-152).

### Spend from the session logs

Where the configuration sets `spend.fromLogs`, the spend above is not summed from records: `spend.mjs` counts it again from the session logs each time `--task`, `--rounds`, `round.mjs` or `done.mjs` asks, with nothing kept between (D-169). The unit of the budget is the goal the statement names on a line `Goal: <goal>`, or else the task itself: a statement with no line is its own unit, with its own limits, and no error (D-179). A reader given the statement's file reads the line from it; one given none, as CI and `round.mjs record` with no statement, reads it from the task's records of the version that applies that copy the statement's lines of the budget, its kept brief of that version, or else its latest record of done of it, onto which `round.mjs brief` and `done.mjs` copy the line, or else its latest snapshot of spend of it, whose `Unit:` is the goal where it is not the task: their line, or its absence, the task's own unit, decides, whatever an older version named; only where no record of that version copies those lines, as for a version whose only record is the owner's approval, the latest line of the task's records of another version. The configuration's `goals` is the composition of each goal: a line that names a goal it does not list, or a goal whose list does not hold the task, is an error of `--task`, `round.mjs` and `done.mjs`, and a record of done or a kept brief whose line is so is an error of the check; a task listed under two goals is an error; the goal's own commands, `--task <goal>`, its record of done and the brief of its acceptance, count it whole by `goals`, its tasks with no line included. The limits come with the version that applies, as [above](#the-budget-of-a-task), and the line does not, so a revised statement given with its line is counted with its goal while the version in force has only the owner's approval as its record. The unit starts at its first brief of a round, or, for rounds written before the writers, at its first round of the review of a statement. The spend of the unit is every event after the start in the executor's sessions, `ONT_EXECUTOR_SESSIONS`, and in the sessions whose first message names the unit or one of its tasks, each event once; the spend of a task of a goal is only the sessions whose first message names that task; the spend of a round is its reviewer's session from the brief to the next brief. The goal's limits and reserve come from its statement, `ONT_GOAL_STATEMENT`, whose version must be the one approved in force. `--task` names the question to the owner when the reserve of the goal or of the task is spent, and then `round.mjs brief` and `done.mjs` refuse, by the same next action with the same limits (D-176); a reader given no logs, as CI, takes the latest snapshot of spend of the version that applies, and with none reads no sums, never a snapshot of another version; `--rounds` shows the sums and names no action by the budget, neither the question nor an overspend to report; after a clean round of acceptance past the reserve, `--task` names on `NEXT` the overspend of the goal and of the task, one part for a goal itself, its own unit, from the logs or, with none, from the round's snapshot, to report to the owner with the merge; `round.mjs record` records a round already briefed as it is. Each round names the snapshot of spend written with it on `Spend-record:`, and `Overspend:` is written only on the round that ends the task with acceptance clean, from that snapshot, which the check, with no logs in CI, compares with it.

## How it fails in practice

- **The table describes an older layout of the repository.** When paths move, update the table in the same change. Include the agent instructions file in the paths that trigger the check.
- **Rules that should be checks stay rules forever.** Review the list from time to time and ask which item could be a check.
- **A correction goes into the instructions by habit.** The agent is told once more in prose, and the next agent repeats the mistake. Ask first whether the code, a check, a test or a lint can make it impossible.
- **Instructions that quietly differ from the approach.** A project's rule says less or more than the rule of the approach it replaces, and nothing records the choice. Write the departure as a process entry and cite it from the instruction.
- **Reviews that list everything.** A finding that misleads no one costs the reader's attention and teaches agents that the list is noise. Report what would mislead a reader or an agent, or would break a check, and leave style and completeness alone.
