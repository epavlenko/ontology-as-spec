# 9. Documentation anchored to the ontology

<!-- ont: ent.doc-section@496f3f, ent.reference-page@b1ec8f -->
## What it is

Documentation for people, written by people or agents, with the ontology as its source. It is treated the way the interface and the code are: an agent or a person writes it from the ontology, it is anchored to concept IDs, and only what restates the ontology is generated by a script.

| | Written from the ontology | Anchored to IDs | Generated by a script |
| - | - | - | - |
| Interface | the mockup | `data-ont` on elements, the map | tooltips |
| Code | code and tests | test tags, the implementation table | contracts |
| Documentation | explanations and guides | an anchor on each section | reference pages: terms, fields, checks; the ontology as a tree |

A section names the concepts it explains in an HTML comment that readers do not see:

```markdown
<!-- ont: action.renew@1709a8, rule.renewal@ee5883, field.loan.renewals@040473 -->
## How renewal works

If you need an item longer, renew it from "My loans". Each renewal adds 14 days …
```

<!-- ont: ent.doc-section@496f3f, ent.reference-page@b1ec8f -->
## Why

Documentation describes the same product as the ontology, in the words of its readers. Without a link between them it drifts the same way design documents and code drift: a rule changes in the ontology, the help page keeps the old one, and nobody notices. An anchor makes the link explicit without filling the text with IDs.

Generating the prose by a script is rejected: explanations say why and how in the readers' words, which no script derives from the rows. An agent writes a page from the ontology like it writes code; the page is then anchored and checked like any other page.

<!-- ont: ent.doc-set@ca5d70, inv.anchors-resolve@974479, inv.doc-set-covers@f46bf8, inv.reference-current@fcb818, inv.doc-set-names-unique@4e4245 -->
## How it is written

- **Anchors.** `<!-- ont: id, id -->` above the heading of the section it describes, with nothing but blank lines between. IDs are concepts or checks. Every section under a heading of the second or third level has one; a section that explains no concept, such as a comparison with other tools or a pointer to the example, has the empty anchor `<!-- ont: -->`, and the check fails on a section with neither. A stamp after `@` is a short hash of what the section relied on when it was last reread: for a concept its term, type and definition and the notes of its section that name it, for a check its case. `stamp-docs.mjs` writes it.
- **Doc sets.** The configuration lists them: a name, unique among the sets, a directory, and the classes whose concepts the set must explain, either the implemented ones (help for users describes what exists) or all of them (a design guide describes the target). A set may also list the proofs whose checks it must name, `"checks": ["manual"]`: that makes it a run guide for the people or agents who run manual checks ([part 6](checks-and-tests.md#running-manual-checks)).

```json
"docSets": [
  { "name": "help", "dir": "help", "cover": ["action", "view", "rule"], "scope": "implemented" }
],
"references": [
  { "out": "help/terms.md", "title": "Terms", "classes": ["ent", "rule", "action", "view"], "implementedOnly": true }
]
```

- **Reference pages.** `gen-reference.mjs` writes each page under `references`: one section per ontology section, a table of the selected classes, and optionally the IDs, kinds, types and the checks of that section.

<!-- ont: ent.doc-set@ca5d70 -->
## Doc sets are process, help in the product is meaning

Which sets of documentation a team keeps, for whom and where, is process, like test suites: it lives in the configuration, not in the ontology. A different team could document the same product differently, and the ontology would not change.

Help that is part of the product is different. A help screen in the app, or a chat bot's answer to "how does it work", is something a user can open or ask for. Those are concepts of the product, rows in the ontology like any other view or action, and their content is anchored and checked like any page. The test is simple: if a user can open it or ask for it, it is product; if it is a file for the team, it is process.

<!-- ont: ent.ontology-tree@159bb0, edge.ontology-tree.concepts@220135, rule.tree-structure-only@08df2d, inv.tree-complete@d8cc81 -->
## The ontology as a tree

To read the whole ontology at once, `gen-tree.mjs` writes it as one page: the configured ontology and the external ones, each table a branch in its order, named by its entity, or by its heading when it has no entity, as the screens of the example. Under each entity are the rows of its table, grouped by kind in the order the configuration lists the classes, with their counts. A row shows its term; its ID and definition appear on hover. A field or relation that refers to an entity shows that entity, and "many" when it refers to several; a view shows the entities it shows. Rules and invariants are marked, and an entity with no other rows says so.

The page shows nothing else: no notes, no links drawn as a graph, no history. Every definition row is in it exactly once, so what is missing from the tree is missing from the ontology. A reference or a view that names an entity the glossary does not define stops the generator with the row, as it fails the check, so the tree never draws a bare ID or drops a link. It is not a hierarchy of classes, as an ontology editor such as [Protégé](https://protegeproject.github.io/protege/views/class-hierarchy/) draws one: the rows under an entity are its table, not kinds of it.

```bash
node tools/ont-check/gen-tree.mjs --config ont.config.json --out /tmp/tree.html --labels labels.json
```

The page is written when someone wants to see the ontology and is not kept in the repository. A labels file, a JSON object, may replace terms by ID, the labels of the kinds it groups rows by, by class, headings of tables without an entity, which are the only headings it shows, and the page's own words, for a reader of another language; the entity keeps its own term beside its label. A key the tree does not show is refused, so a typo or a retired ID does not pass unnoticed.

## Reference

The fields of a doc section, a doc set and a reference page, their rules and checks are in the reference: [Doc section](../reference.md#doc-section), [Doc set](../reference.md#doc-set), [Reference page](../reference.md#reference-page) and [Ontology tree](../reference.md#ontology-tree). Every section declares what it explains: the concepts it is about, or nothing in an empty anchor. Without that, a section the author forgot to anchor would be checked by nobody, since a mention of a concept does not make a section its explanation and the tool cannot tell which sections should have had one. Whether the anchor names what the section is about, and an empty one stands only above a section that explains nothing, is the reviewer's to judge. A stamp says that someone reread the section, not that they got it right, so stamping without reading silences the signal. Pages explain in the readers' words; a page that copies definitions is a reference page written by hand, and should be generated instead.

<!-- ont: rule.anchor-every-section@57e45b, rule.reread-then-stamp@3d0dd6 -->
## How it fails in practice

- **Anchors on everything.** A section that mentions a concept in passing is not an explanation of it. Anchor what the section is about.
- **Stamping in bulk** after a large change to clear the list. The list is the reading plan; clearing it without reading defeats it.
