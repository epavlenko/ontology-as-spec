# 9. Documentation anchored to the ontology

<!-- ont: ent.doc-section@496f3f, ent.reference-page@b1ec8f -->
## What it is

Documentation for people, written by people or agents, with the ontology as its source. It is treated the way the interface and the code are: an agent or a person writes it from the ontology, it is anchored to concept IDs, and only what restates the ontology is generated by a script.

| | Written from the ontology | Anchored to IDs | Generated by a script |
| - | - | - | - |
| Interface | the mockup | `data-ont` on elements, the map | tooltips |
| Code | code and tests | test tags, the implementation table | contracts |
| Documentation | explanations and guides | an anchor on each section | reference pages: terms, fields, checks; the ontology as a tree |

A section names the concepts it explains in an HTML comment that readers do not see:

```markdown
<!-- ont: action.renew@1709a8, rule.renewal@ee5883, field.loan.renewals@040473 -->
## How renewal works

If you need an item longer, renew it from "My loans". Each renewal adds 14 days …
```

<!-- ont: ent.doc-section@496f3f, ent.reference-page@b1ec8f -->
## Why

Documentation describes the same product as the ontology, in the words of its readers. Without a link between them it drifts the same way design documents and code drift: a rule changes in the ontology, the help page keeps the old one, and nobody notices. An anchor makes the link explicit without filling the text with IDs.

Generating the prose by a script is rejected: explanations say why and how in the readers' words, which no script derives from the rows. An agent writes a page from the ontology like it writes code; the page is then anchored and checked like any other page.

## How it is written

- **Anchors.** `<!-- ont: id, id -->` above the heading of the section it describes, with nothing but blank lines between. IDs are concepts or checks. Every section under a heading of the second or third level has one; a section that explains no concept, such as a comparison with other tools or a pointer to the example, has the empty anchor `<!-- ont: -->`, and the check fails on a section with neither. A stamp after `@` is a short hash of what the section relied on when it was last reread: for a concept its term, type and definition and the notes of its section that name it, for a check its case. `stamp-docs.mjs` writes it.
- **Doc sets.** The configuration lists them: a name, unique among the sets, a directory, and the classes whose concepts the set must explain, either the implemented ones (help for users describes what exists) or all of them (a design guide describes the target). Instead of a directory, a set may name its pages one by one, `"files"`: the approach keeps its README, agent instructions, skills and the tool's README in such a set, so that their sections declare what they explain and a stamp says when to reread them, and a README named there is read like any page (D-96). A set may also list the proofs whose checks it must name, `"checks": ["manual"]`: that makes it a run guide for the people or agents who run manual checks ([part 6](checks-and-tests.md#running-manual-checks)).

```json
"docSets": [
  { "name": "help", "dir": "help", "cover": ["action", "view", "rule"], "scope": "implemented" }
],
"references": [
  { "out": "help/terms.md", "title": "Terms", "classes": ["ent", "rule", "action", "view"], "implementedOnly": true }
]
```

- **Reference pages.** `gen-reference.mjs` writes each page under `references`: one section per ontology section, a table of the selected classes, and optionally the IDs, kinds, types and the checks of that section.

## Doc sets are process, help in the product is meaning

Which sets of documentation a team keeps, for whom and where, is process, like test suites: it lives in the configuration, not in the ontology. A different team could document the same product differently, and the ontology would not change.

Help that is part of the product is different. A help screen in the app, or a chat bot's answer to "how does it work", is something a user can open or ask for. Those are concepts of the product, rows in the ontology like any other view or action, and their content is anchored and checked like any page. The test is simple: if a user can open it or ask for it, it is product; if it is a file for the team, it is process.

## The ontology as a tree

To read the whole ontology at once, `gen-tree.mjs` writes it as one page: the configured ontology and the external ones, each table a branch in its order, named by its entity, or by its heading when it has no entity, as the screens of the example. Under each entity are the rows of its table, grouped by kind in the order the configuration lists the classes, with their counts; a class it does not list, as an external ontology may have, comes after them under its own name. A row shows its term; its ID and definition appear on hover. A field or relation that refers to an entity shows that entity, and "many" when it refers to several; a view shows the entities it shows. Rules and invariants are marked, and an entity with no other rows says so.

The page shows nothing else: no notes, no links drawn as a graph, no history. Its footer says what it was built from, and that is not part of the tree. Every definition row is in it exactly once, and the generator refuses to write a tree that would drop one, so what is missing from the tree is missing from the ontology. A reference or a view that names an entity the glossary does not define stops the generator with the row, as it fails the check, so the tree never draws a bare ID or drops a link. It is not a hierarchy of classes, as an ontology editor such as [Protégé](https://protegeproject.github.io/protege/views/class-hierarchy/) draws one: the rows under an entity are its table, not kinds of it.

```bash
node tools/ont-check/gen-tree.mjs --config ont.config.json --out /tmp/tree.html --labels labels.json
```

The page is written when someone wants to see the ontology, or by the hook below, and is not kept in the repository. A labels file, a JSON object, may replace terms by ID, the labels of the kinds it groups rows by, by class, headings of tables without an entity, which are the only headings it shows, and the page's own words, for a reader of another language; the entity keeps its own term beside its label. An ID, a kind or a heading that the tree does not show is refused, so a typo or a retired ID does not pass unnoticed. The page's own words are a fixed list and are always accepted, even where a page does not need one, such as "many" for an ontology with no `refs`, so that one file serves every ontology.

## Keeping the tree current

A clone that keeps a tree for people names its place in its own Git configuration, never in `ont.config.json`, so that the path of one machine does not reach the repository:

```bash
git config core.hooksPath .githooks                                # once per clone, with the other hooks
git config --local ont.treeOut ~/pages/ontology-tree.html          # where this clone keeps its tree
```

After that, a merge into main that Git ends itself in that clone, a fast-forward among them, rewrites the page: the `post-merge` hook builds the tree from the `ont.config.json` at the root of the repository. It writes only when each file it reads, the configuration and the ontologies, is the same as in the commit; if one is changed and not committed, it names the file and leaves the page as it was, since the page would show something main does not have. On another branch, without a place, or after `git merge --squash`, which leaves main where it was, it writes nothing; the squash merge says so. A place inside the repository, its own file or a link to one of its files, is refused with the reason, so that a wrong setting does not overwrite the ontology; a place outside it, such as one in the home directory, is written. If the generator fails, the hook prints the error and the merge stands. Two kinds of merge do not run the hook at all: a merge ended after a conflict with `git merge --continue`, and a real rebase, such as `git pull --rebase` when main has commits of its own; after either, run `node tools/ont-check/gen-tree.mjs --refresh` on main, as below. The hook writes the page in the ontology's own words, without a labels file. A project with a copy of the tool uses the same hook, with the path of its copy in place of `tools/ont-check`.

The footer of the page says what it was built from: the commit, the configuration's path from the root of the repository and the date. A page written with `--out` from files that differ from the commit is marked `+working-tree` after the commit, and one written outside Git is marked no-commit. Each file is compared at the path it was asked for, in the one commit the footer names: a symbolic link, or a path through a linked directory, is never taken as the commit's file, even when the link itself is unchanged and only its target moved.

A clone that serves the page follows main after a merge on the host with `git pull --ff-only`, which ends in a merge and runs the hook. A pull that rebases, or a merge ended after a conflict with `git merge --continue`, ends in a commit instead, and Git does not run `post-merge`. For those, and after a squash merge is committed, the same refresh is run by hand on main:

```bash
node tools/ont-check/gen-tree.mjs --refresh   # what the hook does: main, the place, the root configuration
node tools/ont-check/gen-tree.mjs --stale     # says why the page at the place does not show main, or nothing
```

The stale report names a page that is missing or cannot be read, such as a directory at the place, carries no mark or a mark without its commit, configuration or date, was built from a working tree or outside Git, from another configuration, such as the example's, or from a commit that is not the branch main; it compares with `refs/heads/main`, since a tag named main would be taken for the short name. It says nothing when the page is current or no place is set, and it never fails: a stale page is a page to rewrite, not a broken repository.

## Reference

The fields of a doc section, a doc set and a reference page, their rules and checks are in the reference: [Doc section](../reference.md#doc-section), [Doc set](../reference.md#doc-set), [Reference page](../reference.md#reference-page) and [Ontology tree](../reference.md#ontology-tree). Every section declares what it explains: the concepts it is about, or nothing in an empty anchor. Without that, a section the author forgot to anchor would be checked by nobody, since a mention of a concept does not make a section its explanation and the tool cannot tell which sections should have had one. Whether the anchor names what the section is about, and an empty one stands only above a section that explains nothing, is the reviewer's to judge. A stamp says that someone reread the section, not that they got it right, so stamping without reading silences the signal. Pages explain in the readers' words; a page that copies definitions is a reference page written by hand, and should be generated instead.

<!-- ont: rule.anchor-every-section@57e45b, rule.reread-then-stamp@3d0dd6 -->
## How it fails in practice

- **Anchors on everything.** A section that mentions a concept in passing is not an explanation of it. Anchor what the section is about.
- **Stamping in bulk** after a large change to clear the list. The list is the reading plan; clearing it without reading defeats it.
